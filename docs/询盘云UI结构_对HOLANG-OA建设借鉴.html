复核说明与信息来源
① 本沙箱浏览器受代理限制，未能交互式打开 leadscloud.com 做 DEMO 实测；询盘云 UI 结构来自官网 WebFetch + 第三方评测/演示账号截图描述（52by / 10100 / huoban / xhlbj 等），属厂商营销口径，个别交互细节待 DEMO 实测核实。
② holang-oa 结构来自源码核对：MainLayout.tsx、App.tsx、Dashboard.tsx、CustomerDetail.tsx，置信度高。
③ 核心判断：我们在客户360 / 时间轴 / 全渠道概览 / 销售闭环上已具备询盘云的「结构骨架」，差距主要在触点数据自动抓取与CRM 自动化规则引擎，而非页面形态本身。因此借鉴重点是「补数据来源 + 加规则引擎」，无需重构现有 UI。

1. 询盘云 UI / 信息架构（IA）

1.1 总体组织逻辑：全触点（Touchpoint-Centric）

导航按「客户触点」而非「业务域」组织：WhatsApp / 企业微信 / 网站交互 / Facebook / Instagram / 邮件。每个触点一个模块，所有触点数据统一汇入 CRM 客户池。

导航（全触点） ├ 首页工作台（仪表盘 / 运营小工具） ├ CRM（核心·所有渠道客户沉淀点） │ ├ 客户列表 │ └ 客户360（时间轴） ├ WhatsApp ├ 企业微信 ├ 网站交互（建站 + 流量监测） ├ Facebook ├ Instagram ├ 邮件管理（资料库 / 群发单显） ├ 销售漏斗 / BI 报表 └ 流程 / 自动化配置

1.2 首页工作台（仪表盘）

  • 运营小工具：个人名片、世界时钟、WhatsApp 号码归属地查询、国际疫情实时统计、货币兑换、日程任务表。
  • 业务驾驶舱：新询盘数、「7 天未跟进」客户数（可点击穿透）、销售漏斗分布（各阶段可点击）、日程安排、客户跟进记录；支持按时间段查看、灵活筛选定位。

1.3 客户360（CRM 核心）

  • 每个客户一条「时间轴」，记录全生命周期行为/交互轨迹，便于观察状态变化与复盘。
  • 详情页集成：询盘 + 联系人全部信息及操作；可切换查看「同一客户每个询盘」的进展 / 文档 / 任务。
  • 支持「复购」场景：同一客户多个询盘的追踪与管理。

1.4 客户旅程时间轴（招牌能力）

  • 自动抓取并关联各触点：WhatsApp / 企微 / 网站 / Facebook / Instagram / 邮件。
  • 顶部筛选条：按类型分时序（跟进记录 / 邮件 / 网站交互 / 企微 / FB / WhatsApp / IG / 来源）+ 数量统计；全视角客户画像。

1.5 销售漏斗

支持企业自定义漏斗阶段，每个阶段可点击穿透查看该阶段客户详情，实时掌握跟进进度。

1.6 客户流转

支持客户转移 / 分享 / 退公海；可自定义自动退公海规则（如超 N 天未跟进）；为业务员设置客户上限，让全公司客户有效流转。

1.7 流程 / 自动化（可视化流程设计器）

  • 拖拽式定义全流程规则：线索分配 → 跟进提醒 → 合同审批 → 回款确认。
  • 示例规则：「超 3 天未跟进自动流转公海」「合同金额 > 10 万需总监审批」。
  • 协作：团队负责人可查看下属邮件；可标记重点客户提醒上级；可分享询盘给同事联合跟进。

1.8 营销侧

SEO 服务、网站流量监测（个体访客行为追踪）、Shopify / Magento 订单打通、邮件企业资料库、群发单显（变量替换）。

2. holang-oa 现有 UI / IA（源码核对）

2.1 总体组织逻辑：业务域（Domain-Centric）

侧边栏按业务域分组，契合「业财一体化」定位；带两层身份隔离（管理员/用户）+ RBAC 菜单过滤，与询盘云取向不同但合理。

导航（业务域） ├ 工作台 Dashboard（可拖拽 widget） ├ 产品 Product ├ CRM·内销 domestic（customers/leads/opps/quotations/orders/collections/deliveries） ├ CRM·外销 export（同上 + whatsapp + proforma） ├ 售后 aftersales（visits/tickets/returns） ├ SRM（suppliers/inquiries/orders/receive/payables） ├ ERP（生产/仓储/财务） ├ 数据分析 analytics ├ 组织 org（contacts/roles） └ 系统工具 tools（approval/templates/feishu-wiki/...）

2.2 工作台（Dashboard）—— 已较强

  • 固定 TopStatsBar：待办 / 已批 / 逾期 / 催办（可点击穿透）。
  • 可拖拽自定义 widget：my_customers / leads / opps / quotations / orders / collections、stats、pipeline（销售漏斗 SVG）、recent_activity、notifications、custom_page（iframe）。
  • 按角色默认布局 + 管理员可设默认 + 自定义页面。

2.3 客户360（CustomerDetail）—— 结构已齐

  • Tab：概览 / 联系人 / 商机 / 报价 / 订单 / 回款 / 时间轴 / AI 助手。
  • 销售闭环 stepper（商机→报价→合同→订单→回款）——这是我们领先询盘云的能力。
  • 跟进阶段进度条；全渠道互动概览（已按 WhatsApp/电话/邮件/官网/社媒 统计）。
  • 社媒账号关联（占位 Phase 2）。
  • 时间轴 Tab：渠道筛选 + 时间范围筛选 + 父子回复树 + AI 辅助生成 + 主管补充。

2.4 外销触点入口（现有）

/export/whatsapp（原型页）、/marketing/{campaigns,leads,channels,seo}。

2.5 审批 / 自动化（现有）

ApprovalEngine（审批专用：模板 / 统计 / 流转），非通用 CRM 自动化规则引擎。

4. 反哺建设清单（按优先级，含复用点）

原则：保持 holang-oa 为唯一客户主数据（SoR），不整体引入询盘云；前端触点按渠道 ROI 分级补强，与 2026-08-17 渠道结论（官网SEO / FB·IG / Google ADS）一致。

P0 · 内部复用·零新依赖
  • P0-1 工作台「N 天未跟进预警」卡片：复用 Dashboard.tsx 的 WIDGET_REGISTRY + TopStatsBar 模式，新增 widget unfollowed_alert，显示「7 天未跟进客户数」点击穿透到对应 lead/customer 列表。直接对标询盘云驾驶舱。
  • P0-2 销售漏斗可穿透：PipelineWidget 各阶段点击 → 跳 /analytics/opportunities 或对应列表；阶段枚举改为可配置（复用 oppStage 字典）。
复用：Dashboard widget 机制、TopStatsBar 穿透、oppStage 枚举、现有 followUp 数据
P1 · 外销前端补强（对齐渠道结论）
  • P1-1 官网访客追踪埋点 → 自动建外销 lead + 写入时间轴（channel="官网" 已支持）。回流 holangintl.com 询盘。
  • P1-2 WhatsApp / 社媒互动自动归档进客户时间轴：复用 CustomerDetail timeline 多 channel 模型（website/social/whatsapp 类型已定义），接入抓取层。
复用：LeadPool、CustomerDetail 时间轴 channel 模型、FollowUpService
P2 · CRM 自动化引擎（补齐规则层）
  • P2-1 轻量 CRM 自动化规则引擎：超 N 天未跟进 → 自动退公海；客户上限；跟进提醒。复用 ApprovalEngine「规则 + 触发」思路，但独立于审批避免耦合；作用于 LeadPool / 客户池。
  • P2-2 多维度查重：外销 lead 入库时按 公司名/邮箱/电话/WhatsApp/社媒 校验，防重复建档（先核实现有查重能力再补）。
复用：ApprovalEngine 规则范式、LeadPool 公海、现有客户字段
P3 · 协作与营销（按需）
  • P3-1 客户/商机「分享 + 标记重点」给上级/同事：把现有 timeline 主管补充机制扩成显式分享（对标询盘云分享/标记）。
  • P3-2 外销实用小组件：世界时钟 / 货币换算 / WhatsApp 归属地，作为 Dashboard 可选 widget。
  • P3-3 邮件群发单显 / 资料库：外销渠道不含邮件，低优先。

5. 实施原则与风险

  • 不整体引入询盘云：其「客户旅程时间轴」价值需履约数据支撑，而履约在 holang-oa；整体采购 = 花 SaaS 年费只买「获客采集器」，性价比低（详见对比报告）。
  • 复用优先：Dashboard widget、CustomerDetail 时间轴多 channel、ApprovalEngine 规则、LeadPool 公海——均已存在，补的是「数据来源」与「规则层」。
  • 风险：① 自动抓取需合规账号（WhatsApp Business / Meta 审核），周期与驳回风险易被低估；② 多触点关联需统一身份解析（同一客户跨渠道去重）；③ 去重与自动退公海规则误伤需灰度。
