> 生效：2026-10-27 刘总裁定。本文件为**长期治理基线**，跨会话延续；与 `docs/OA_增量推进_主线支线规划.md`（进度追踪）配合使用。

## 0. 双方法论定义（最高优先级，所有支线强制执行）

### 方法论 A：GitHub FIRST（遇新问题先看开源成熟经验）
- **本义**：遇到不会的 / 新的问题，**不闭门造车、不胡编乱造**，先到开源项目里找成熟的成功项目经验或方法论，站在巨人肩膀推进当下工作。
- **配套（另一条规则 · 备份铁律，勿混淆）**：改动先本地 `commit` 进 `system-build` + 生成离线 `*.bundle`（落 `F:/HOLANGbuddy/03_项目资产/`）供刘总 A 路径推送；沙箱**不执行 `git push`**（需刘总授权）。
- 凡"新问题"先问「开源成熟项目怎么做」，再对照自身实现找差；不为尚未验证的假设直接下判。

### 方法论 B：增量开发（一次只解决一件事）
- **本义（刘总 2026-10-27 最终定义）**：一次只解决一件事，逐项完成某个项目的推进完成。**换而言之：一个支线解决一次问题，禁止发散。**
- **支线动态可调（刘总 2026-10-27 补充）**：支线的顺序与内容**不是一成不变**——可根据每次支线任务反馈回的情况灵活调整顺序或增删内容；但每个支线仍须遵守"单一问题、不发散"红线。
- **北极星目标**：Sales CRM 固定总纲（帮销售高效完成 需求→选型→报价→谈判→Contract/PI→Order→收款 闭环）。所有支线最终对齐此目标。

## 1. 角色与分工

| 角色 | 职责 |
|---|---|
| **主线（协调者 = AI 执行体 / 本会话 holang-pde）** | 把握方向、定义方法论、派单、验收核验、**统一 commit + 生成 bundle**、向你汇报；遇问题统一安排，不在支线内自行扩散 |
| **支线（执行体 = 主线派生的隔离子 Agent）** | 承接主线派发的**单一**任务，在红线内执行（只读复核 or 限定改动），做完按固定格式汇报；遇问题只**上报**不越权决策 |

> 说明：本会话"主线"与"支线"均为同一 AI 能力的两个视角，靠隔离保证不发散；"技术建设专家"是支线子 Agent 的角色标签，非独立外部人。

## 2. 支线纪律（红线，强制）
1. 只承接主线派发的**单一**任务；
2. 不扩大范围（不顺手修无关 bug、不加功能、不重构）；
3. 做完即汇报；
4. 遇问题记录并上报主线。

## 2.5 汇报契约（触发时机 + 格式 + 通道）—— 刘总 2026-10-27 裁定补充

> 目的：支线一多若汇报无约定必然乱。本契约把"什么时候报 / 怎么报 / 走哪条通道"写死，全线强制执行。

### A. 触发时机（WHEN）—— 三类必须报
1. **任务完成即报**：无论成功 / 部分完成 / 失败，支线执行结束**第一时间**回主线，不静默。
2. **中途遇阻即时报**（不自行决策，上报等主线统一安排）：
   - ① 出现**超出派单范围**的依赖或阻塞；
   - ② 与现有技术债务 / 红线（第 3 节越界清单）冲突；
   - ③ 任何需刘总或人工兜底的越界事项。
3. **无进展也播报**：超出预期时点仍无结论，须发「状态播报」（进行中 / 卡点 / 预计何时出结果），禁止失联。

### B. 汇报格式（HOW）—— 固定五段结构化短报
支线汇报**必须**包含以下五段，不写"做完了"三个字就结束：
1. **已完成**：一句话结论 + 是否达成分派目标（✅/⚠️/❌）。
2. **修改文件**：清单 + 关键 `file:line` 实证（供主线核验）。
3. **验证方式**：实际跑过的命令与结果（`tsc --noEmit` / `vite build` / 单测 / 验证脚本）。
4. **风险点**：未解决的、需主线安排的、需人工兜底的，逐条列清。
5. **待主线安排**：下一步建议（可选方向 + 推荐项 + 待拍板）。

> **证据外置原则（省主线上下文）**：上述五段只放**摘要与指针**；完整证据（全量 diff、日志、报错原文、核验截图说明）一律写入 `docs/支线X_汇报_YYYYMMDD.md`，主线仅保留 **≤15 行摘要 + 文件路径** 回灌上下文，按需读文件核验。禁止把大段原始 diff / 日志堆进主线对话。

### C. 汇报通道（CHANNEL）
- **路径 A（当前推荐 · 已落地）**：支线在本会话隔离执行，把完整汇报写盘到 `docs/支线X_汇报_YYYYMMDD.md`，主线收到≤15行摘要后**按需读文件核验**，不挤占主线 token。
- **路径 B（新开对话做支线 · 刘总 2026-10-27 提议）**：支线在独立对话执行，做完把汇报文件落盘 + 向主线发一句指针（结论 + 文件路径）；主线在新轮次读文件做独立核验。
- **禁止项**：① 大段原始 diff / 日志 / 报错堆进主线对话；② 只说"做完了"不附证据指针；③ 跨会话丢失汇报文件（必须落盘 `docs/`）。

### D. 主线收口动作（承接汇报后）
读 `docs/支线X_汇报_YYYYMMDD.md` → 独立核验（`git diff` + 重跑校验，不盲信子代理自述）→ 出 / 更新验收签字单 → 统一 commit + 重新生成 bundle（见第 4 节闭环）。

## 3. 不越界清单（AI 执行体严禁，须由人或授权人兜底）
- 生产服务器起停 / 实例重建（如 CVM 恢复）；
- 真推 GitHub（`git push`，须刘总 A 路径带 PAT）；
- 生产库迁移 / schema 推送 / 任何 DB 写操作；
- 密钥、令牌、`.env` 的读取 / 打印 / 提交（一律 `<REDACTED>` / 占位符）；
- 对外通知（企微 / 邮件）的内容与通道授权；
- 跨工具协同中需独立人工 / 工具授权的部分。

## 4. 验收签字机制（闭环）
1. **支线执行完** → 输出：已完成 / 修改文件 / 验证方式 / 风险点 / 剩余步骤。
2. **主线独立核验**：`git diff` 复核 + 重跑 `tsc --noEmit` / `vite build`（**不盲信子代理自述**）。
3. **出签字单**：参照 `docs/OA已落地模块-验收签字单-2026-10-06.md` 与本会话 CRM 签字单范式——功能 → 核验点 → 代码实证(file:line) → 结论（✅/⚠️/❌），标注「待刘总签字」。
4. **主线统一 commit**（安全项 / 功能项分离）+ 重新生成离线 bundle（`git bundle verify` 须 OK）。
5. **工作区保持** `git status` 全清；敏感校验 `NO_SENSITIVE`（无 `.env` / `*.db` / token 入库）。
6. **生产运行验收**待服务器恢复后补做（见支线4 启动清单）。
