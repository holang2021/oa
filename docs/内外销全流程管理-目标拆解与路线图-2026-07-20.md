## 一、业务目标拆解（目标型诉求必做）

### 1. 原始需求
- **提出人**：刘总（总经理）
- **原话**：「公司内外销全部管理起来，从获客到过程及售后的全流程管理」
- **本质**：不是"建某个模块"，而是要一个**覆盖内外销、贯穿客户全生命周期的数字化载体**

### 2. 真实业务目标
- **目标**：内外销客户全生命周期（获客 → 过程 → 售后）数字化闭环，管理者随时可见、可追溯、可分析
- **目标类型**：① 收入提升（转化/复购）② 效率提升（过程可见、减少口头跟进）③ 风险降低（客户资产沉淀、合规留痕）
- **影响范围**：销售、售前、财务、售后、管理层全角色；内外销双通道

### 3. 成功指标（可量化）
| 维度 | 核心指标 | 当前状态 | 目标状态 |
|------|----------|----------|----------|
| 获客 | 询盘/线索入库率、来源分布 | 库 leads=0，无系统承载 | 100% 入库、来源可见 |
| 过程 | 线索→商机→报价→订单转化率、订单→回款周期 | 不可见（企微/口头） | 各阶段转化率可统计 |
| 售后 | 工单响应时长、质保到期提醒、复购率 | 无 | 响应可追踪、复购可识别 |
| 系统 | 双通道上线、数据线接通率、员工周活跃 | 仅地基通、前端跑 mock | 双通道上线、数据 100% 接通 |

### 4. 根因分析
- **人员**：销售过程责任在系统外（企微/口头），不可见、不可追溯
- **流程**：获客→售后无统一载体；内外销两套习惯、无统一客户池
- **数据**：394 客户散落、无 channel 标；products/leads/opportunities=0；无售后数据
- **系统**：设计已定（含询盘云外销参考），但**没建成**——数据线未插、页面缺一半。系统确是缺口，但地基（C1）已通

### 5. 数字化判断
- **判断：A 需要数字化建设**（高频 + 重复 + 跨部门 + 数据价值明显）
- **理由**：客户资产是公司生命线，且已确认业务规则（双通道/询盘=线索/全触点/PI），只需把"设计"落成"系统"，无需重新决策业务

### 6. 下一步建议
- **立即**：按本路线图 Phase 1 起步，外销首版先见产值
- **后续**：内销补齐 → 售后 → 全触点 → 智能
- **进入数字化项目评估**：是（本路线图即评估结论）

## 三、全流程蓝图（获客 → 过程 → 售后，**双系统架构**）

> **架构定调（2026-07-20 16:09 刘总最终裁定）**：**客户资产池统一（一份主数据，不重复、不丢客户）+ 双运营系统（内销 / 外销各自独立一套运营系统，线索/商机/报价/订单/回款/售后彻底分开跑）**。即"统一池 + 双系统"，非单系统内双模块。

```
                      ┌──────────────────────────────────────┐
                      │   统一客户资产池（主数据一份）            │
                      │   customers / contacts 共享，只录一次    │
                      └───────────────┬──────────────────────┘
                                      │ 被两套运营系统共同引用
            ┌─────────────────────────┴─────────────────────────┐
            │                       │                             │
   ┌────────▼─────────┐                          ┌───────────────▼─────────┐
   │  外销运营系统      │                          │  内销运营系统             │
   │  (独立一套)        │                          │  (独立一套)               │
   │ 获客:询盘(展会/    │                          │  获客:线索(官网/转介绍/    │
   │  官网/社媒/代理/   │                          │  投标)                    │
   │  海关)            │                          │  过程:线索→商机→跟进→     │
   │ 过程:询盘→商机→   │                          │  报价(合同)→订单→回款     │
   │  跟进→报价(PI·    │                          │  售后:安装→质保→维修→     │
   │  CI/PL)→订单→    │                          │  备件→复购                │
   │  回款             │                          │                           │
   │ 售后:同上         │                          │                           │
   └────────┬─────────┘                          └────────────┬──────────────┘
            │                                               │
            └──────────── 复购/转介绍 回流统一客户池 ─────────┘
   侧轨：全触点接入（企微 / WhatsApp / 邮件）→ 两套系统各自沉淀跟进记录
```

**关键设计点（沿用已确认规则，不再重议）：**
- **统一客户主数据**：客户档案 / 联系人只存一份，内销外销共用，杜绝重复录入与丢客户
- **双运营系统**：内销、外销各跑一套完整运营（获客→过程→售后），数据物理/逻辑隔离，互不打扰
- 外销询盘 = 线索(Lead)；商机简化 4 档；跟进走全触点（对标询盘云）
- 外销报价内嵌 PI/CI/PL，内销报价走合同/人民币发票
- 售后闭环末端「复购」回流统一客户池，形成生命周期

## 四、分阶段实施路线图

> 原则：止血 → 增能 → 智能。每阶段前验收不过不进后阶段。执行方按此推进，本图只规划。

### Phase 0 — 地基（已完成，2026-07-20）
- ✅ 后端连生产库、前端骨架、双库消除、API 验证通过
- 状态：**已成，不作为后续阻塞**

### Phase 1 — 外销首版（止血 + 增能，先见产值）⭐ 起点
- **目标**：外销从询盘到回款可在系统内走通，数据真实
- **范围**：
  - 外销客户页（接真实 API）+ 询盘(Lead)页 + 商机页(4档) + 跟进页
  - 报价页（接 3001，含 PI/CI/PL 打印，去空端口 3002/3003）
  - 订单回款页（接真实 API）
  - 数据线接通：前端 login/客户/订单/回款/询盘/商机/跟进 全调 3001
  - 数据清洗：394 客户打 `channel=外销` 标 + 去测试数据
  - 上线切换：新前端部署上线、旧系统退场（部署由技术团队执行，我不下服务器指令）
- **交付物**：外销首版可用系统、上线清单、数据清洗脚本说明
- **验收**：外销询盘→回款全流程在系统内跑通 1 条真实业务；数据线接通率 100%
- **依赖**：Phase 0；技术团队接手

### Phase 2 — 内销运营系统补齐（增能）
- **目标**：内销运营系统复用统一客户池 + 外销框架，独立跑通
- **范围**：内销客户/线索/商机/跟进/报价(合同/人民币发票)/订单回款；引用统一客户池
- **复用**：统一客户主数据（一份）+ Phase 1 的 API 层、页面模板、引擎，仅差异化单据流与运营隔离
- **验收**：内销运营系统全流程跑通；与统一客户池打通，不重复录客户

### Phase 3 — 售后全流程（增能）
- **目标**：获客→过程→售后闭环补全
- **范围**：售后工单、安装调试记录、质保管理（到期提醒）、维修、备件、满意度、复购识别
- **复用**：客户池 + 订单关联；复购回流获客层
- **验收**：售后工单可建可追踪；质保到期可提醒；复购客户被识别

### Phase 4 — 全触点集成（智能）
- **目标**：对标询盘云「全触点管理」，过程自动沉淀
- **范围**：企微 / WhatsApp / 邮件 统一收件箱，自动建跟进记录；跨触点时间线
- **验收**：外部沟通进系统后自动生成跟进，无需手工录

### Phase 5 — 数据看板与智能（智能）
- **目标**：管理者驾驶舱 + 自动化
- **范围**：获客来源 ROI、转化漏斗、订单→回款周期、复购预测、异常自动提醒
- **验收**：管理层看板可用；关键指标周报自动推送

## 五、优先级与"先见产值"策略

| 优先级 | 阶段 | 理由 |
|--------|------|------|
| P0 | Phase 1 外销首版 | 出口是主营收、1000+客户、数据已在库；先跑通降整体风险 |
| P1 | Phase 2 内销 | 复用框架，成本低 |
| P1 | Phase 3 售后 | 闭环必需，但可晚于内销（售后依赖过程数据） |
| P2 | Phase 4 全触点 | 提效明显但非首版阻塞 |
| P2 | Phase 5 智能 | 数据积累后价值最大 |

> 注：你定的是"双系统同步首版"范围（内销外销两套运营系统一起建），但排期上我仍建议**外销运营系统先跑通**（同属首版程序、两个里程碑），这是降风险的建序建议，不推翻范围决定。

## 六、风险与负责人提示

1. **双系统工作量**：内销外销各一套独立运营系统，工作量约为单系统 2 倍；但客户主数据只建一份（统一池），可省去重复录入与客户去重。对冲：外销先跑通、内销紧随。
2. **双系统部署形态待定**（新增决策点）："共享客户主数据 + 双运营系统"是架构概念，落地形态需技术团队在 Phase 1 前定——是**单代码库部署两个实例**（共享库或各自库）还是**两套独立代码**。建议单代码库双实例，运维轻、客户池天然统一。
3. **数据清洗隐形坑**：394 客户无 channel 标，清洗时必须补标 + 去测试数据（Q7 定"部分真实需清洗"）。注意：客户主数据统一后，channel 标仍要打在运营数据上区分内外销业务。
4. **空端口 3002/3003**：报价/审批前端依赖两个不存在的后端。决策：并入 3001 还是新建，由技术团队定。
5. **范围重度**：79 功能对 11 人超重。本路线图已砍到首版外销核心链路，后续按需扩展，避免一次铺开。
