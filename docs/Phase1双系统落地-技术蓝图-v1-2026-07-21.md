## 一、部署形态拍板建议（移交清单"待拍板 3 点"）

> 总原则：落地形态 = **① 单代码库双实例**，统一客户主数据表 + 运营数据 `salesType` 行级隔离。下面三点逐一拍板。

### 1.1 双实例数据共享粒度 → **共用一张 `customers` 主数据表（推荐）**
- **推荐**：外销/内销实例读同一张 `customers`（及 `contacts`）表；运营数据（orders/payments/leads/opportunities/quotes/invoices/deliveries/follow_ups）同库同表，靠 `salesType` 行级隔离，**不拆表、不拆库**。
- **为什么**：① 正中刘总"统一客户资产池，不重复不丢客户"裁定；② schema 已预埋 `salesType`（`customers` line 65、`orders` line 183、`payments` line 280 等多表均有 `@@index([salesType])`），行级隔离顺水推舟；③ 一份表天然杜绝双系统客户重复录入/去重难题。
- **边界（什么不做）**：❌ 不采用形态②（各自独立库）——需客户同步机制，违背"统一池"且运维翻倍；❌ 不在 Phase 1 做物理分库分表（留给 Phase 2+ 演进）。

### 1.2 部署隔离级别 → **同服务器双进程（初期），环境变量区分域**
- **推荐**：一份代码库，两个进程/两次前端构建，用环境变量区分：
  - 外销实例：`VITE_SALES_TYPE=EXTERNAL`（构建期注入）、后端进程读同一库。
  - 内销实例（Phase 2）：`VITE_SALES_TYPE=INTERNAL`。
- **为什么**：运维最轻（一份代码、双进程）；Phase 2 内销复用外销框架、零边际成本；后期若需强隔离可平滑拆容器/独立域名，不推翻架构。
- **边界（什么不做）**：❌ Phase 1 不做双域名 HTTPS 网关 / 双容器编排（I1 仅配 env + 构建变量，上线动作由人类技术方执行）；❌ 不做强物理隔离。

### 1.3 登录与权限 → **共用一套鉴权 + server-side 数据域强制**
- **推荐**：双实例**共用同一 3001 后端 + 同一 JWT + 同一 `users` 表**；但**新增 `salesDomain` 数据域服务端强制约束**（本蓝图核心安全决策，源于 0.1 发现的"后端实例无感知"缺口）。
  - 登录时，实例把自身 `VITE_SALES_TYPE` 写入 JWT claim `salesDomain`（或用户 profile 绑定 `salesType` 数据域）。
  - 后端新增 `enforceSalesDomain` 中间件：① 列表查询**以 JWT.salesDomain 为准强制 `where.salesType`**（忽略前端 query，防越权）；② 写操作校验目标记录 `salesType ∈ 当前域`；③ 无域 claim 的跨域请求 403。
- **为什么**：用户/角色必须统一（避免双份账号体系、RBAC 重复维护）；但"内销实例不能误改外销客户运营数据"是硬红线，当前仅靠前端 query 过滤**不安全**，必须服务端兜底。
- **边界（什么不做）**：❌ 不新建第二套账号/鉴权体系；❌ Phase 1 不做跨域管理员（每用户只属一个 `salesDomain`）；❌ RBAC 角色沿用现有 `users.role`（SALES/MANAGER/ADMIN），不扩展。

## 三、主数据规范（D1–D3 + 统一约束）

### 3.1 D1 — 394 客户 `salesType` 补填 EXTERNAL 规则
- **字段已存在**（`customers.salesType` 默认 `"INTERNAL"`），仅补值，无需迁移。
- **自动分类规则（CodeBuddy 写脚本，人类技术方在备份后执行）**：
  - `EXTERNAL` ← `country IS NOT NULL AND country <> '中国'` **或** `businessLine = 'RETAIL'` **或** 存在 `contacts.whatsapp` 非空。
  - `INTERNAL` ← `country IS NULL OR country = '中国'` 且 `businessLine = 'INDUSTRIAL'` 且无 whatsapp。
  - **歧义行** → 导出 CSV（含 id/companyName/country/businessLine/有无whatsapp）交**刘总人工确认**（不靠 AI 猜）。
- **为什么**：HOLANG 主营工业气体设备出口，外销为主营收；但"内销/外销"是业务判定，不能凭空猜测，故规则 + 人工复核双保险。
- **边界**：❌ 不自动把全部 394 标 EXTERNAL（需尊重真实内销客户）；❌ 不改动 `customerCode`/`huobanId` 唯一键。

### 3.2 D2 — 测试/演示数据清除
- 执行前**强制备份** `holang-crm.db` → `holang-crm.db.bak-20260721`（人类技术方执行，红线）。
- 清除规则：删除 `remark/notes/source` 含 `test/mock/演示/测试` 且非真实订单回款关联的记录；保留 394 真实客户 / 283 订单 / 458 回款。
- **边界**：❌ 不清真实业务记录；❌ 不在未备份时删数据。

### 3.3 D3 — 校验
- 脚本跑后断言：`COUNT(customers WHERE salesType='EXTERNAL')` + `INTERNAL` = 394；`orders/payments` 按 salesType 过滤条数与预期一致；`leads/opportunities/products=0`（设计有、未建，符合预期）。

### 3.4 客户主表统一约束
- 已存在唯一：`customerCode`(line 49)、`huobanId`(line 105)。
- **Phase 1 仅加应用层去重校验**（同一 `salesType` 下 `companyName` 不重复录入），**不强制 DB 唯一约束**——避免迁移破坏历史 394 数据。
- **边界**：❌ 不在 Phase 1 加 `(companyName, salesType)` 联合唯一索引（风险 > 收益）。

### 4.2 统一 API 层封装（`src/api/client.ts`）
- 读 `import.meta.env.VITE_API_BASE`（默认 `http://localhost:3001`）。

- 401 自动 `refresh` 或跳登录；统一错误结构 `{code, message}`。
- 导出 `api.get/post/put/del(path, body?)`。
- **为什么**：消灭散落 `fetch(localhost:300x)`、统一鉴权与域参数，是 A1 的落点。

### 4.3 去掉 3002/3003 依赖的改造规则
- 全局替换：`QuotationCenterPage.tsx:15`、`QuotationListPage.tsx:11`、`FormDesignerDemo.tsx:13` 的 `http://localhost:3002` → 改用 `src/api/quotes.ts`（表单数据走 3001）。

- **验收**：全仓 `grep -r "localhost:3002\|localhost:3003"` 结果为 0。

### 4.4 approval-engine 接入 3001 的方式

## 八、最大技术风险（提示）

1. **后端"实例无感知"未补 = 双实例隔离失效**（最高风险）：当前仅靠前端 `?salesType` 过滤，内销实例改 URL 即越权。**必须 B1 server-side `salesDomain` 强制** 作为 P0 首件，否则"统一池 + 双系统"红线破裂。
2. **数据清洗歧义**：394 客户自动分类可能误标，需刘总复核 CSV；且清测试数据前必须备份，否则不可逆。
3. **空端口债蔓延**：3002/3003 散落 5 处，A3 改造遗漏任一即页面调不通——以 `grep` 机检兜底。
4. **后端缺口连锁**：lead 无写接口、approval 无表、dashboard 无过滤、PI/CI/PL 无端点——B 系列是前端 P 系列的前置阻塞，须先完成。
