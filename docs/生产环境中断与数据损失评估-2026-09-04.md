# 生产环境中断与数据损失评估（复核修正版 v2）

**出具日期**：2026-09-04
**版本说明**：v2 为压迫式复核后的修正版，**推翻了 v1 的一处核心论断**。v1 曾判定"数据停在 7 月上旬、损失约两个月、商机链不可恢复"，经复查**该判定夸大**，本文给出修正后的准确结论。
**性质**：实查报告（全部结论来自实测，非记忆推断）
**用途**：恢复决策依据；可转发腾讯云技术支持或其他专家

## 〇、v1 → v2 修正摘要（务必先读）

| 项 | v1 判定（错误） | v2 判定（修正后） | 判据 |
|---|---|---|---|
| 备份时间点 | "文件时间戳 8-11 不代表新鲜度，数据实际停在 7 月上旬" | **备份就是 8-11 14:57 的真备份，时间戳准确** | 审计日志 286 条全部落在 2026-08，最后一条 `2026-08-11 14:57:01`，与文件 mtime 14:57 完全吻合 |
| 数据缺口 | "7 月中至 8 月底，约两个月" | **8-11 14:57 → 8-27 服务器回收，共 16 天** | 备份有效时间点 8-11 + 实例回收日 8-27 |
| 商机/报价/合同/产品/PI | 归入"已丢失的数据" | **不是丢失，是当时本来就没有**（表已建、模块已上线、业务数据未录入） | 5 张表 `CREATE TABLE` 均存在且为空；审计日志显示 8-11 用户已正常查询这些模块 |
| 损失定性 | "商机链不可恢复，需接受" | **商机链无损失**（本就空表）；真实损失集中在用户体系与客户归属 | 见第三章 |

> ⚠️ v1 的失误教训已记录：SQLite 动态类型下，同一列混存 TEXT 与 INTEGER 时，`MAX()` 会按类型排序（数字永远排在字符串前），导致整数时间戳被完全忽略。v1 对 `users` 表的统计因此漏掉了 8-11 的毫秒时间戳记录，进而误判整库新鲜度。v2 已按 `typeof()` 分组重算。

## 五、三种情景与应对

### 情景 A：腾讯云有快照（最佳）
1. 用快照恢复云盘 → 取回 8-27 的完整数据库
2. 新建实例 → 按现有部署结构还原（前端 `/opt/holang/oa/app`、后端 PM2 `holang-oa-backend:3001`、nginx `/api/` 反代）
3. **数据零损失**，且能补回 8-11 后的用户体系、角色体系、客户归属

### 情景 B：无快照（损失有限，路径明确）
1. 用备份恢复：394 客户 + 联系人 / 跟进 / 订单 / 发货 / 发票 / 回款 / 合同主体全部在
2. 重跑企微通讯录同步 → 重建 20+ 员工账号与 15 角色体系
3. 复用 8-17 理顺方案 → 重新分配客户归属
4. 商机 / 报价 / 合同 / 产品 / PI：本就为空，**按原计划录入，无额外损失**
5. 唯一实质遗留：8-11 至 8-27 间可能新增的少量跟进记录

### 情景 C：有部分快照或旧镜像
以快照时间点为准，重复 A 流程，再按 B 补齐快照之后的部分。

## 六、待决策事项

1. **【最紧急】腾讯云控制台核查实例快照**（轻量应用服务器 / 云服务器 → 快照列表），并确认实例状态是"已销毁"还是"已退还"
2. 若确认无快照：确认接受情景 B，启动重建（损失集中在用户体系与客户归属，均有重建路径）
3. **备份机制缺陷必须解决**：本次仅有 8-11 一次手工备份，间隔过长。重建时需建立自动化每日异地备份，否则同类风险会再次发生

## 附：v2 复核方法说明

| 复核动作 | 目的 |
|---|---|
| `sqlite_master` 全表枚举 + 逐表 `COUNT(*)` | 确认空表是"不存在"还是"存在但为空" |
| 按 `typeof()` 分组重算 `MAX(时间列)` | 规避 SQLite 动态类型导致的时间戳漏统计（v1 失误点） |
| 审计日志按月分布 + 末条时间戳比对文件 mtime | 交叉验证备份真实时间点 |
| 双归属字段 `salesOwnerId` / `owner_id` 分别核验 | 避免漏查备用归属列 |
| `_prisma_migrations` 迁移记录 | 判断库结构演进阶段 |

*数据来源：本地只读数据库盘点 + 网络探测 + 后端实跑演练。全程未写入任何业务数据。*
