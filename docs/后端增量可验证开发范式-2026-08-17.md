# HOLANG OA 后端「增量可验证 / 低耦合 / 影响隔离」开发范式

> 依据：刘总 2026-08-17 指令（第一性原理 + 压迫式审核）
> 适用范围：OA 后端（含数据迁移/导入管线、部署脚本）的全部后续开发
> 配套脚本：`holang-oa/deploy/huoban_migration/{converters/, verify_modules.py, patch_sales_type.py}`、`wecom-app-1000081/deploy/{deploy_patch.py, ship_and_run.py}`

---

## 一、四条铁律（本次确立）

1. **模块可独立验证**：后端拆成可独立运行、可即时验证的功能模块。每完成一个模块，必须提供「可直接观测的运行效果或接口验证方式」，刘总无需等整体完成即可确认进展。
2. **低耦合架构**：模块间只通过清晰接口（列 / 外键 / API 契约）通信。任何单点修改不得引发全局连带故障；若存在强耦合，必须重构解耦。
3. **变更影响隔离**：新增或修复功能时严格限定作用域，禁止无必要触碰无关代码 / 数据，杜绝「全量返工」式浪费。
4. **交付附验证步骤**：每个模块交付时，附明确验证命令，使刘总能直接观测该模块实际效果。

## 〇、任务启动门禁——如何规避「先写后端」（刘总 2026-08-17 追问的答案）

**根因**：上轮我把「实现数据的真实导入」当成纯后端活儿，直接冲 ETL 管线，跳过了「先出可见效果」。铁律「先可见效果后后端」在记忆里，但我没把它当**任务开场硬门禁**执行，所以又犯了。

**门禁（每个任务开场强制执行，不跨线）**：

1. **拆两半**：收到任何「功能 / 实现 / 导入」类需求，第一动作不是写代码，而是把任务拆成「可见层」+「后端层」两半。
2. **先交可见层**：先出刘总能直接看 / 点到的东西——前端徽章 + 筛选预览（`present_files` 看实物），或（纯后端任务）一份可跑的验证报告。
3. **不跨线确认**：明确告知「本次先出可见效果 X，确认后再写后端 Y」；不拿到刘总明确「直接上后端」指令，不碰后端。
4. **后端自成验证闭环**：确需写后端时，按本范式拆成可独立验证模块（如 `converters/` 包），每模块配一条 `verify` 命令，让刘总无需等整体就能看到每个模块对不对。

> 这条门禁已固化为工作记忆铁律，每次任务开场自检。

## 二、对「上方已完成后端工作」的压迫式复核（已实读源码，非凭记忆）

上一轮为完成「内销/外销真实导入」，我写了 `huoban_to_crm.py` / `load_huoban_to_oa.py` / `clear_oa_business.py` / `oa_deploy_business_reload.py`。逐文件压迫式复核，发现 **5 处不合理**，均违反上述铁律：

| # | 不合理之处 | 违反 | 证据（源码定位） |
|---|---|---|---|
| F1 | **不可见效果**：数据全量部署完成后才在末尾做一次 `COUNT` 校验，过程中无任何模块级断点验证；刘总无法在中间确认进展。 | 铁律1、4 | `oa_deploy_business_reload.py` 第 78-119 行：清表→重导→重灌→push→重启全塞进一个 shell heredoc，仅末尾 `COUNT` |
| F2 | **强耦合 + 单点连带故障**：单体 `set -e` 脚本，一次 `arcname` 路径笔误（`deploy/huoban_migration` 少一层）即让 `load` 找不到文件，`set -e` 使 `pm2 restart` 未执行 → **整个 backend 停在 stopped**。单点错误引发全局停服。 | 铁律2 | `oa_deploy_business_reload.py` 第 59 行 `arcname` + 第 79 行 `set -e` + 第 98 行 `pm2 restart` 在失败分支不执行 |
| F3 | **冗余全量返工（最严重）**：为修 3 个内外销标签 bug（orders 取错字段 / deliveries 硬编码 / customers 小写），执行 `clear_oa_business`（**清空 9 张业务表**）+ 全量重导（~2000 行）。这是无影响隔离的「全量返工」，且当时有清库风险（若 OA 内有用户自建数据会被误删）。 | 铁律3 | `clear_oa_business.py` 清 9 表；`oa_deploy_business_reload.py` 第 92-96 行清表+重导 |
| F4 | **部署不可增量**：每次部署都重打整个 `crm_output`（~2MB → 20+ TAT 分块），即使只改 1 个字段也要全量上传。无「只部署某模块」能力。 | 铁律1、3 | `oa_deploy_business_reload.py` 第 56-65 行整目录 tar |

## 三、逐一修改后的新机制（已落地，已验证）

### 3.1 可即时验证的模块校验器 → 解决 F1/F4 验证缺口
**`verify_modules.py`**（只读，`PRAGMA query_only=ON` 防误写）
- 定义 6 个独立模块，每个一组断言：
  - `客户标签`：businessLine↔salesType 一致、无小写脏值
  - `订单标签`：同上
  - `发货继承`：deliveries.salesType == 父 orders.salesType（0 不一致）
  - `回款继承`：payments.salesType == 父 orders.salesType
  - `开票继承`：invoices.salesType == 父 orders.salesType
  - `发货明细`：delivery_items = 301 条 / 关联 245 发货单
- 输出 ✅/❌ 报告 + 总判定；`--module 名称` 可单模块验证。
- **已实跑生产（只读）**：6 模块全部 ✅。

### 3.2 影响隔离的定向补丁 → 解决 F3 冗余全量返工
**`patch_sales_type.py`**
- 只改受影响的 3 张子单据表（deliveries/payments/invoices）的 `salesType` 列，用 `JOIN 父订单` 相关子查询推导。
- **不清表、不重导、不碰** users/customers/orders/contacts/leads/opportunities/follow_ups/contract_entities/order_items/products/quotes/delivery_items（脚本显式声明白名单反向约束）。
- `--dry-run` 先看影响范围；幂等（重跑一致）。
- **已验证**：合成库演示——故意制造 3 处错位（D3/P2/I1），真实补丁精准修正这 3 行，customers/contacts 等无关表纹丝不动。

### 3.3 通用定向补丁运行器 → 解决 F2 单点连带故障
**`deploy_patch.py`**（替代全量 reload 巨石）
- 检查点流程：上传补丁+校验器 → **备份生产库**（回滚点）→ 前置校验 → 停服→补丁→**末尾强制 `pm2 restart`**（杜绝停摆）→ 后置校验 → 失败自动从备份回滚。
- **去掉盲目 `set -e`**，改为每步显式判定 + 末尾强制重启。任一步失败 → 回滚 + 重启 + 报 FAIL，绝不留服务停摆。
- 与 `verify_modules.py` 联动：补丁前后都验指定模块。

### 3.4 转换器彻底解耦 → 解决 F5 隐式全局耦合（已落地，2026-08-17）
**`huoban_to_crm.py` 708 行巨石 → `converters/` 包（每实体一文件 + 编排层）**：

```
converters/
├── __init__.py          # 统一导出所有转换器 + run
├── helpers.py           # 解析辅助（resolve_* 显式接收 item_index，无全局隐式依赖）
├── source.py            # 导出源加载（schema/data/field_map/item_index），纯数据层
├── employees.py         # convert_employees
├── customers.py         # convert_customers / convert_contacts / convert_leads
├── opportunities.py     # convert_opportunities（convert_quotes 已备，待用）
├── orders.py            # convert_orders / convert_order_items
├── transactions.py      # convert_payments / convert_invoices / convert_deliveries / convert_followups
├── contract_entities.py # convert_contract_entities
└── orchestrator.py      # run()：编排顺序 + 输出落地，不含任何转换逻辑
huoban_to_crm.py         # 薄入口：定位导出源 + 调 converters.run()
```

- 每模块可**独立 import + 喂小数据单测**（客户[海外]→EXTERNAL/RETAIL、发货自身外贸→覆盖父订单、回款继承父 EXTERNAL 等全部通过），不依赖整条管线。
- 隐式全局耦合彻底消除：`resolve_*` 全部显式接收 `item_index`；`order_sales_map` 由编排层构造后逐层显式传入。
- **行为零变更验证**：用真实导出跑新旧两套管线，12 个 JSON / 3499 条记录逐字节 `ALL_OK`；部署位置 `import converters` + `py_compile` 均通过。
- 原始 708 行保留为 `huoban_to_crm.py.bak`，可随时回退。

## 五、后续后端模块的交付承诺

- 每做完一个后端模块，**先跑 `verify_modules.py` 对应模块**（或新增该模块的断言），把 ✅ 报告作为交付物一并给你。
- 修 bug 一律走 `patch_sales_type.py` 式**定向补丁 + 影响隔离白名单**，禁止「清表全量重导」。
- 部署一律走 `deploy_patch.py` 的检查点流程（备份→校验→补丁→重启→回滚），杜绝单点连带停服。
- 已解耦的 `converters/` 包，后续只改对应实体文件；其他能用的代码同理，只在触碰时按铁律3 增量解耦。
