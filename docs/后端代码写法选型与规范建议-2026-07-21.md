## 〇、结论先行（给刘总的一句话版）

**不用换框架，也不用换语言。** 全家桶已是 TypeScript，现在就把 Express 补上**严格分层（Controller / Service / Repository）+ 统一类型与响应契约**，这套"写法"就是刘总要的"前卫、好迭代、好维护"——本质是**借 Java 的"规矩"（分层/契约/测试），留在 TS 的"地盘"（好招人/好前后端统一）**。换 Java 或盲目追 NestJS/Hono 都是把已投的钱和进度推倒重来，当前不划算。

**推荐方案：A（Express 4 + 立即补严格分层 + 沿用 Prisma/zod）。** ★★★★★
**（备选升级路线：当团队 >20 人或领域 >30 模块时，再评估 NestJS；不阻塞 Phase 1。）**

## 一、"前卫、好迭代、好维护"的可量化标准

> 刘总原话："我不懂名词，我要前卫、好迭代、好维护。" 下面把这三个词翻译成**可验收的指标**，用来评判任一候选方案。每项都能机检或人工核对，避免空谈。

| 维度 | 含义（人话） | 可量化标准（验收口径） | 当前 HOLANG 现状 |
|------|--------------|------------------------|------------------|
| **1. 分层清晰** | 改一处不乱全局 | ① 业务改动只动 `services/`，不动 `controllers/`；② 任一 handler ≤ 30 行；③ 无 `services/` 之外的文件直接 `new PrismaClient()` | ❌ 现状：业务逻辑全在 controller，单文件 700+ 行（customer.controller.ts） |
| **2. 类型安全** | 编译期抓错，少线上 bug | ① `tsconfig` 开 `strict: true`；② 边界（HTTP 进出）有 zod；③ `services/` 签名 0 个 `any`；④ Prisma 查询经 Repository 包一层 | ⚠️ 现状：TS 有但 controller 内 `where: any` 遍地的 `as any` |
| **3. 易加功能** | 新人也能加接口 | 新增一个标准 CRUD 端点：改动文件 ≤ 3 个（route+controller+service），新增 LOC ≤ 80（不含测试） | ❌ 现状：加功能要在 controller 里复制粘贴 zod+prisma+response 三件套 |
| **4. 易换人维护** | 人走了代码接得住 | ① 新员工按目录即可定位代码（约定优于配置）；② 核心逻辑有单测，覆盖率 ≥ 60%；③ `grep "<实体>" src/` 能一次找全 | ❌ 现状：逻辑散落，无单测，依赖原作者记忆 |
| **5. 生态活跃** | 框架别哪天死了 | 框架 npm 周下载量、GitHub Stars、近 12 个月发版频率、社区问答量 | Express 最稳；NestJS 第二；Hono 新但小 |
| **6. 招人难度** | 在本地/国内招得到 | TS/Node 候选人供给 vs Java 候选人供给（工业气体 CRM 场景）；11 人团队养得起 | ✅ TS 易招；❌ Java 后端在 HOLANG 场景难招且割裂前端 |

**总监判定**：第 1/2/3/4 项（分层/类型/迭代/维护）是"前卫好维护"的真正来源，**它们由"写法规则"决定，不由"框架名字"决定**。第 5/6 项（生态/招人）决定框架不该乱换。

## 二、候选写法对比（至少 3 个，含推荐度）

> 评分口径：前卫度=架构现代感；可迭代性=加功能/改功能成本；迁移成本=相对当前 Express 代码库的改造代价（★越多越省）；招人难度=越低星越易招；风险=落地不确定性。

### A. 保持 Express 4 + 立即补严格分层（Controller/Service/Repository）+ 沿用 Prisma/zod
- **前卫度**：★★★☆（Express 本身"老"，但 TS+strict+zod+Prisma+分层 这套组合是 2024+ 现代基线，不落伍）
- **可迭代性**：★★★★★（分层后加接口只动 service；复用现有全部投资）
- **迁移成本**：★（**极低**——不换框架，只补层；现有 route/controller 文件结构保留，逐模块重构）
- **招人难度**：★（Node/TS 在 CRM/工业 SaaS 场景极好招，与前端同语言）
- **风险**：★（最低——零架构颠覆，Phase 1 不阻塞）
- **说明**：把 Java 的"分层纪律"搬进 Express；用 TS 的强类型 + zod 边界 + Prisma 类型查询补齐"类型安全前卫感"。

### B. 升级 NestJS（TS 原生、Spring 式 DI/模块/装饰器）
- **前卫度**：★★★★★（TS 生态里最"像 Java 规范"、最工程化，装饰器+依赖注入最潮）
- **可迭代性**：★★★★★（模块化/DI 让大型系统极好扩展，最契合"未来扩 ERP/仓储/生产"）
- **迁移成本**：★★（**高**——所有 controller 改写成 `@Controller`+`@Injectable` 装饰器，路由改装饰器，需引入 module Providers 体系；相当于一次后端重写）
- **招人难度**：★★（TS 仍好招，但 NestJS 专精人才少于 Express 通才）
- **风险**：★★★（高——会**阻塞 Phase 1**（B 系列已基于 Express 开发）；11 人团队短期用不上其全部复杂度；学习曲线拖慢首版）
- **说明**：最接近刘总嘴里"Java 的规则"，但它是**语言内的规则升级**，不是换 Java。适合作为**未来升级路线**，不是现在。

### C. 迁移 Hono（轻量极速、Edge-ready）
- **前卫度**：★★★★（新锐、性能强、天然适配边缘/Serverless）
- **可迭代性**：★★★（轻，但分层/规范**全靠自己建**，团队要自建"规矩"）
- **迁移成本**：★★（高——API 风格与 Express 不同，middleware/路由全改；且要自己搭分层约定）
- **招人难度**：★★★（Hono 较新，国内工业 CRM 人才池薄）
- **风险**：★★★★（高——生态小、企业级 ORM/事务/权限脚手架少；对"未来扩 ERP"支撑弱；等于为"快"牺牲"稳"）
- **说明**：适合做轻量 API 网关/边缘函数，**不适合作为 HOLANG 主 CRM 后端的主框架**。

### D. （备选）Fastify（Schema-first、高性能、Express-like API）
- **前卫度**：★★★★（内置 schema 校验/序列化，TS 友好）
- **可迭代性**：★★★★（插件体系 + 与 Express 相似的写法，迁移比 NestJS 平滑）
- **迁移成本**：★★★（中——API 接近 Express，但 middleware/错误处理/插件机制要改；仍需迁移）
- **招人难度**：★★（Node 圈认知度高，但专精略少于 Express）
- **风险**：★★（中——仍是框架切换，有迁移债；收益相对 A 不显著）
- **说明**：比 NestJS 迁移轻，但**相对 A 仍是"为切换而切换"**，无压倒性收益。可作 B 的平价替代备选。

### 对比总表
| 方案 | 前卫度 | 可迭代性 | 迁移成本(省★) | 招人难度(易★) | 风险 | 推荐度 |
|------|--------|----------|---------------|---------------|------|--------|
| **A Express+分层** | ★★★☆ | ★★★★★ | ★（最省） | ★ | ★ | **★★★★★（推荐）** |
| B NestJS | ★★★★★ | ★★★★★ | ★★（贵） | ★★ | ★★★ | ★★★☆（未来路线） |
| C Hono | ★★★★ | ★★★ | ★★（贵） | ★★★ | ★★★★ | ★★☆（不推荐主框架） |
| D Fastify | ★★★★ | ★★★★ | ★★★（中） | ★★ | ★★ | ★★★☆（备选） |

## 三、明确推荐 + 理由（含"是否真换 Java"立场）

### 3.1 推荐：方案 A（Express 4 + 严格分层 + Prisma/zod 不变）

**为什么（逐条对应刘总诉求）：**
1. **前卫**——"前卫"≠框架新潮，=**现代工具链 + 严谨架构**。TS strict + zod 边界校验 + Prisma 类型化查询 + 分层 + ESLint/Prettier，这套在 2026 是工业级现代基线；Express 只是 HTTP 壳，壳不决定"前卫"，里面的写法才决定。
2. **好迭代**——分层后，加一个客户/订单/回款接口只动 `services/<实体>.ts`，controller 只是"接参数→调 service→回响应"的薄壳，新人照模板抄即可。当前"复制 zod+prisma+response 三件套"的重复劳动被消灭。
3. **好维护**——业务逻辑从 700 行 controller 收拢到 service，可单测（不依赖 HTTP/DB 即可测规则）；人走了代码接得住；`grep` 一次找全。
4. **成本/进度**——100% 复用现有 Express+Prisma+zod+TS 投资，**Phase 1 不阻塞、不重写**；已有 `response.ts`/`errorHandler.ts` 直接变规范底座。
5. **招人**——Node/TS 与前端同语言，11 人团队养得起、本地好招；不引入 Java 招聘瓶颈。

### 3.2 明确立场：不换 Java，也不盲目追 NestJS

- **换 Java = 不划算（强烈不建议）**：全家桶已是 TS（前端 React+TS、后端 TS）。换 Java 等于**后端重写 + 与前端割裂（两套语言/两套构建/两套招人渠道）+ 成本翻倍 + 招聘变难**。除非有强理由（如强事务一致性要求上 Java 生态专有中间件），否则**否决**。刘总之前记成"Hy3 vs Java 规则"——现已澄清他只在乎结果；结论是：**采纳 Java 的"规则"（分层/契约/测试），但留在 TS 的"地盘"**。
- **NestJS 是"未来升级路线"，不是现在**：当团队 >20 人或业务域 >30 个模块（ERP/仓储/生产陆续上线）时，NestJS 的 DI/模块治理优势才显性化。届时在 A 的分层基础上平滑迁移（service 层可大概率平移），**现在上 NestJS 是为未到的规模提前付重写税**。
- **Hono/Fastify 不作主框架**：Hono 太轻缺企业脚手架；Fastify 相对 A 无压倒收益。二者仅作"未来若需极致性能/边缘部署"的备选，不进 Phase 1。

### 3.3 升级触发条件（写死，避免日后反复）
满足**任一**即重新评估 B（NestJS）：
- 后端全职研发 ≥ 5 人，或总研发 ≥ 20 人；
- 业务域模块数 ≥ 30（当前约 20）；
- 出现跨多域的强一致事务 + 复杂调度（如 ERP 与 CRM 共用事务），Express 分层难以治理。
未触发前，**一律走 A**。

## 四、迁移成本与风险（针对 Phase 1）

### 4.1 方案 A 的迁移成本（极低，且可增量）
- **不换框架、不换库**：Express/Prisma/zod/TS 全保留；只把"平铺 controller"重构为"薄 controller + service + repository"。
- **增量可行**：Phase 1 的 B 系列（B1~B4、B5）**边写边按新分层写**，等于用新规则写新功能，零回退。已存在的老模块（customer/order 等）作为**参考模板**择机重构，不阻塞首版。
- **具体动作（交给 CodeBuddy）**：
  1. 建 `src/services/<实体>.service.ts`（放业务逻辑）、`src/repositories/<实体>.repository.ts`（放 Prisma 调用）、`src/schemas/<实体>.schema.ts`（放 zod DTO）；
  2. controller 改为只做：zod 解析入参 → 调 service → 用 `utils/response.ts` 回包；
  3. 删除各 controller 内 `const prisma = new PrismaClient()`，改用注入的 repository。

### 4.2 若选 B（NestJS）的迁移成本（高，阻塞 Phase 1）
- 需把 20+ 个 controller 改写为装饰器风格、引入 `@Module`/`@Injectable`/DI 容器、重写 middleware 为 guards/interceptors；Phase 1 已开发的 B 系列要返工。**会阻塞首版上线 2~4 周以上**，且 11 人团队短期收益不匹配成本。

### 4.3 最大风险对照
| 风险 | 方案 A | 方案 B/C/D |
|------|--------|------------|
| 阻塞 Phase 1 | 否（增量） | 是（重写） |
| 推翻现有投资 | 否 | 是（部分/全部） |
| 招人变难 | 否 | 是（Java/NestJS专精） |
| 架构颠覆导致 bug | 低 | 中~高 |
| 未来扩展性 | 够用（触发条件内） | 更强但当前用不上 |

**结论：方案 A 不阻塞 Phase 1，且是风险最低的前进路径。框架切换类方案统一判定为"不阻塞条件不满足"，不在 Phase 1 窗口内启动。**

## 五、代码规则定义（无论选哪个，定死的规范）

> 以下规则**立即生效**，作为 CodeBuddy 写码与验收的硬约束。已存在的 `utils/response.ts`、`middleware/errorHandler.ts` 作为底座直接采用。

### 5.1 分层契约（核心：哪层干什么，哪层不干什么）
```
routes/<实体>.routes.ts     → 只声明 HTTP 方法/路径/中间件链；不含逻辑
controllers/<实体>.controller.ts → 薄壳：解析 JWT/params/body → zod 校验 → 调 service → 用 response 回包；≤30 行/函数
services/<实体>.service.ts  → 业务逻辑唯一归属：规则、权限、聚合、事务编排；纯 TS，不碰 req/res
repositories/<实体>.repository.ts → 唯一允许写 Prisma 的地方；返回领域对象/数组
prisma/schema.prisma        → 数据模型与迁移；Repository 之上不再有 DB 访问
```
**禁令（机检兜底）**：
- ❌ controller / route / service 内出现 `new PrismaClient()`（仅 `repositories/` 与启动处允许）；
- ❌ service 内 import `express` 或读取 `req/res`（保持可单测）；
- ❌ controller 内写 `prisma.xxx.findMany` 等业务查询（必须过 service→repository）；
- ❌ 跨层 `as any` 逃逸类型（service 签名 0 `any`）。

### 5.2 命名约定
- 文件：`kebab-case`；实体类：`PascalCase`；函数：`camelCase`。
- service 类：`<Entity>Service`；repository：`<Entity>Repository`；方法语义化：`list/create/update/remove/assign`。
- zod DTO 文件：`schemas/<entity>.schema.ts`，导出 `create<Entity>Schema` / `update<Entity>Schema`。
- 统一响应结构 `{ code, message, data }`（`code:0`=成功，非 0=业务/错误码）。

### 5.3 统一错误处理
- **必须用**现有 `AppError`（已在 `errorHandler.ts` 定义）：业务失败 `throw new AppError('客户不存在', 404)`，由全局 `errorHandler` 统一转 `{code,message,data}`。
- **禁止**在 service/controller 里手写 `res.status(404).json({...})` 散弹式返回（现状 customer.controller 的通病）。
- `errorHandler` 已覆盖 `ZodError`/`PrismaClientKnownRequestError`/`JsonWebTokenError`/`AppError`，**维持并补全**：新增 `Prisma P2003`（外键）友好提示。

### 5.4 统一 API 响应结构
- **强制**使用 `utils/response.ts` 的 `success()/error()/paginated()`，禁止 controller 内联手写 `{ code:0, message:'获取成功', data }`（现状不一致，需整改）。
- 分页接口一律 `paginated(list, page, pageSize, total)`，前端 `src/api/client.ts` 已约定该结构。

### 5.5 日志规范
- **禁止** `console.log/error` 散落（现状 `errorHandler.ts` 用 `console.error`）。改用结构化日志库（**建议 pino**，轻量、JSON 输出、TS 友好）。
- 规范：请求入口/出口、关键业务动作（建单/审批/回款）、外部调用（企微/微信）均落结构化日志，含 `traceId`/`userId`/`entity`。
- 生产环境不打印 stack 到响应（现状 `errorHandler` 已对 dev/prod 区分，保留）。

### 5.6 必要的测试门槛
- **service 层单测强制（交付门槛）**：每个 `<Entity>Service` 核心方法（创建/状态流转/权限判定/聚合）必须有 vitest 单测，用 mock repository，**不依赖真实 DB**。
- **覆盖率门槛**：service 逻辑行覆盖 ≥ 60%（首版）；后续逐步提到 70%+。
- **契约测试**：zod schema 变更需有"非法入参被拒"用例。
- 现有代码无测试 → CodeBuddy 补分层时同步补该实体 service 单测；不达标不视为完成。

### 5.7 类型安全底线
- `tsconfig.json` 开 `strict: true`（含 `noImplicitAny`）——现状若是宽松模式，列为 P0 整改。
- 所有 HTTP 边界用 zod 校验（入参），出参类型由 `ApiResponse<T>` 约束。
- `country` 字段当前用 `$queryRawUnsafe` 绕过 Prisma（customer.controller.ts:136/252）——**列为技术债 P1**：把 `country` 补进 `schema.prisma` 并通过 Repository 正常查询，消灭裸 SQL。
