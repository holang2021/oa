# 离职移交与公海治理分析（2026-07-22）

> 刘总点名的第一件事。治理分析，待刘总随问随确认（不攒批）。

## 一、现状回顾（已定基线）
- **统一客户池 SoR**：一份公司主数据，国内=统一社会信用代码、海外=邓白氏码(DUNS) 为唯一键。
- **客户聚合根（刘总 14:55 定）**：**客户(Customer)是所有从属信息的聚合根**——联系人、商机、报价、合同、订单、回款、开票、售后、跟进、异动等全部挂在客户下，**随客户整体移动，不拆分、不单独分离**。移交/退公海/分配 = 移动客户聚合整体，下面的子实体一并走。这与"统一客户池(主数据一份)"架构裁定一致。
- **公海机制**：线索公海（独立）+ 客户公海 & 商机公海（**共用一套引擎、底层分实体**，用 `pool_type` 区分 customer / opportunity）。
- **内销/外销绝对分离**：所有公海按 `salesType` 服务端强制隔离（H-2 防下载）。
- **RBAC**：管理员/主管可操作公海与分配。

## 二、离职场景
员工 X 离职，手上持有：客户(`owner_id=X`)、商机(`owner_id=X`, 进行中)、在途报价/合同/订单/回款跟进。

## 三、三种出口（主管裁量，刘总 14:49 定）
### A. 一键移交指定人（全部）
- 主管/管理员选 X → 选接手人 Y（**须同 salesType**，因内外销绝对分离）→ 批量转移客户+商机+在途跟进。
- 带「**交接包**」：客户资料 + 商机进展 + 待办 + 合同/回款状态，Y 接手即见全貌。
- 不进公海、客户不丢、关系不断。
- audit_log：`X离职, N客户/M商机 移交 Y, by 主管Z, time`。

### B. 退回公海（兜底）
- 无接手人 / 主管决定重分配 → X 的客户条目(`in_public_pool=true, pool_type=customer`)、商机条目(`in_public_pool=true, pool_type=opportunity`)，`owner_id=null`。
  - 进入客户公海/商机公海（同一引擎分实体）。新 owner 认领。

### C. 部分移交（主管勾选）
- 主管对 X 的客户/商机**逐批勾选**：一部分转接手人 Y1、一部分转 Y2、余下退公海（任意组合）。
- 每次部分转移仍带「交接包」（该批次客户资料 + 商机进展 + 待办 + 合同/回款状态）。
- 适用：离职人业务需拆分给不同接手人的真实场景（比"全交一人"更贴合实际）。
- audit_log：`X离职, 部分 N1客户/M1商机→Y1 + N2/M2→Y2 + 余 K 退公海, by 主管Z`。

## 四、是否同一个公海
- **是**。按已定设计，客户公海+商机公海=同一引擎、分实体。离职"退公海"即客户类进 customer 池、商机体进 opportunity 池。**与刘总"同一个公海也行"一致**，无需拆两套。

## 五、关键风险（防"裸退公海"）
- 在谈商机/未结订单不能简单丢公海完事；**因「客户聚合根」原则，客户+其下全部商机/合同/回款/跟进整体随客户进公海，认领人看到的是完整聚合而非散件**——这从数据模型层面化解了"接手人接不住"的风险，交接包不再需要单独拼装。
- 剩余需团队统一的设计细节：未结业务退公海是否需主管二级确认、交接包精确字段、主管自身离职的二级机制、历史数据看不可改。

## 六、建议方案（待确认后入总纲+流程图）
- 离职移交 = 独立治理动作，做成「**移交工作流**」：
  - 触发：HR/管理员标记员工离职（状态=离职, 禁用登录）。
  - 主管在三种方式中裁量选择（一键全部移交 / 部分移交 / 退公海），不留空、不留裸退。
  - 一键全部移交：选同 salesType 接手人 → 批量转 + 交接包。
  - 部分移交：主管勾选分批转不同接手人，余下退公海，每次带交接包。
  - 退公海：客户类→客户公海, 商机体→商机公海。
  - 审计 + RBAC（仅管理员/主管可发起）。
- 进总纲框架（公海设计补全）+ 流程图（公海区加「离职移交/一键移交」入口）。

## 七、已定决策（刘总）
- **Q1 已定（14:49）**：离职移交提供**三种方式**，由**主管裁量决定**用哪种——①一键全部移交指定人 ②部分移交（勾选分批转不同接手人）③退公海。系统提供三种操作入口，主管按实际情况组合，不预设"主从"。
- **客户聚合根已定（14:55）**：客户下所有从属信息随客户整体移动，不拆分。移交/退公海 = 移动客户聚合整体。

## 八、Q2–Q6 已统一结论（2026-07-22 多方讨论 2 轮收敛，无升级项）
> 依 SOP 第三节"已确认问题由团队讨论直到达成统一"，本议题（Q1+聚合根已确认下的细化）经 tech-lead/gas-sales/de-arch 两轮交叉讨论，全数收敛一致。详见 docs/离职移交-多方讨论纪要-2026-07-22.md。

- **Q2 轻量二级确认**：主管点退公海 → AI 自动弹未结业务清单(预填+大额标红) → 主管看一眼点"确认退公海"即生效（一次性点选不阻断）；原因可选备注(非必填)；确认动作留痕(操作人+时间戳+未结清单快照)作审计。守 H-3（AI 不代签）。
- **Q3 自动摘要+可选备注**：不维护独立交接包持久化字段（唯一真相源=聚合快照）；系统自动生成交接摘要卡片(AI读快照→NL总结:进展/卡点/待办/风险)必出；可选自由文本"交接备注"(非必填,挂事件流水不新建实体)供手写隐性信息，移交触发时主动提醒填写、建议化非强制。
- **Q4 主管自身离职**：数字员工自动检测主管=离职且无触发人 → 告警上级/管理员 + 移交任务重路由；上级主管/管理员可越级代发起(复用Q1一键逻辑)，不卡流程。
- **Q5 历史看不可改**：历史记录(created_by/历史跟进/已归档合同)只读(前端只读视图+服务端写拦截)；现owner对进行中可改；允许新建跟进挂原客户(写新不改正)；RBAC自动切只读。
- **Q6 署名保留**：owner_id变更不改created_by/历史author(不可变)；UI区分"当前负责人/原创建人"；退公海认领/移交后自动打"原负责人X(已离职)"标签，默认显示可追溯不覆盖。
