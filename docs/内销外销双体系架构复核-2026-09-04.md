## 1. 当前内销/外销隔离架构（现状）

**隔离发生在"角色 → 派生域"与"数据标签"两层，不是两套独立系统。**

- **User 无 salesType 字段**。隔离由 `role` 经 `deriveSalesType(role)` 派生：
  - `INTERNAL_SALES / INTERNAL_LEAD / INTERNAL_SUPPORT` → 域 `INTERNAL`
  - `EXTERNAL_SALES / EXTERNAL_LEAD / EXTERNAL_SUPPORT` → 域 `EXTERNAL`
  - `ADMIN / FINANCE / AFTER_SALES / READONLY_AUDIT` 等 → 域 `ALL`（跨域）
- **数据层标签**：`Customer` 与 `Order` 模型**直接带 `salesType`（INTERNAL/EXTERNAL）+ `businessLine`（INDUSTRIAL/RETAIL）**，且建了 `@@index([salesType])`。
- **域强制中间件** `enforceSalesTypeScope`（`middleware/salesType.ts`）：非全域角色，自动在 `req.query.salesType` 注入其域，下游支持 salesType 过滤的控制器只返同域数据；并写 `req.scope` 供服务层判断。
- **`filterByUser`**（`rbac.ts`）：纯销售角色只看本人 `salesOwnerId` 名下数据。
- **挂载该中间件的路由**：customer / opportunity / order / payment / pi / quote / contract（routes 均 import 并 use `enforceSalesTypeScope`）。

**关键设计意图（代码已编码）：**
- `contract.service.ts`：内销商务合同**仅 INTERNAL 域可建**；外销域越权拦截（注释："D3 外销走 PI"）。
- `deal-flow.service.ts`：`assertContractConfirmed` 要求合同 `salesType=INTERNAL`；`assertPiConfirmed` 要求 PI `salesType=EXTERNAL`。
- `Order` 模型同时有 `contractId`（内销商务合同）与 `piId`（外销 PI）两个可空外键。
- `Pi` 模型：`salesType EXTERNAL 外销专用`，`currency` 默认 `USD`。

→ 结论：**系统从一开始就被设计为"一个客户池 + 两套流程"，并非一条统一流程加条件分支。** 内销=合同路径，外销=PI 路径，下游履约（发货/发票/回款）共用。

## 2. 内销真实业务链（当前实际系统）

代码意图链（内销）：
```
Customer(INTERNAL) → Quote(RMB, taxRate=13) → Contract(INTERNAL, 强制)
  → Order(contractId) → Delivery → Invoice(增值税票) → Payment
```
外贸特有字段检查（内销 Quote/Order 模型实测）：
- ✅ `taxRate` 默认 13（增值税）、`amountWithoutTax`（未税）、`discount`、`invoiceType`、`taxTitle/taxNumber`（开票信息）、`receiverAddress`（国内收货）
- ❌ 无 currency（默认 RMB，无字段）、无 Incoterms / Port / Freight / Packing / HS Code / 币种

**生产数据真相**：内销 orders=265，但 `contractId` 全为 0（contracts 表 0 行）→ **内销生产订单并未挂合同**，直接建单。上半段（Quote/Contract）在数据中同样为空。

→ 内销生产实际跑的是：`Customer(INTERNAL) → Order(直接) → Delivery → Invoice → Payment`（含税/未税字段在用，合同/报价未用）。

## 3. 外销真实业务链（当前实际系统）

代码意图链（外销）：
```
Customer(EXTERNAL) → Quote(taxRate=0) → PI(EXTERNAL, USD) → Order(piId)
  → Delivery → Invoice → Payment
```
外贸特有字段检查（实测）：
- ✅ `Pi.currency`（默认 USD）、`Pi.salesType=EXTERNAL`、`Quote.taxRate` 注释"外销统一 0"
- ❌ `Quote` 模型**无 currency 字段**（外销报价单不记录币种，币种只在 PI 出现）
- ❌ `Order` 模型**无 currency / Incoterms / Port / Freight / Packing / HS Code / Payment Terms / Exchange Rate**
- ❌ 全模型无 Commercial Invoice / Packing List / 报关字段 / L/C-T/T 付款方式结构化

**生产数据真相**：外销 orders=18，但 `piId` 全为 0（pis 表 0 行）→ **外销生产订单同样未挂 PI**，直接建单。Quote/PI 在数据中为空。

→ 外销生产实际跑的与内销同构：`Customer(EXTERNAL) → Order(直接) → Delivery → Invoice → Payment`，仅客户/订单的 `salesType=EXTERNAL` 区分。PI/报价未使用。

## 6. 当前数据模型冲突（重点：Customer / Opportunity / Quote / Order）

1. **Customer 共享主档 + 允许跨域重名**：`companyName` 仅 `@index` 非 `@unique`，`huobanId` 唯一但那是迁移源 ID。当前 0 例跨域同名，但**系统允许**同一公司建两条（一条 INTERNAL、一条 EXTERNAL）。潜在问题：同一企业既做内销又做外销时，会分裂成两个客户主档，跟进/订单/业绩统计被割裂。【需业务确认】
2. **联系人/跟进接口未做服务端域隔离**：`contact.routes.ts`、`followup.routes.ts` 未挂载 `enforceSalesTypeScope`，`contact.controller.ts` 无 salesType 过滤，且 `Contact` 模型无 salesType 字段。内销销售理论上可经 API 读取外销联系人（域只靠前端或父客户间接约束）。**这是真实隔离漏洞**。
3. **Quote 缺 currency 字段**：外销报价单无法记录币种，而 PI 才补 USD。外销"报价→PI"传递币种时出现断层，且 Quote 本身表达不了外贸报价。
4. **Order 缺外贸字段**：Incoterms / Port / Freight / Packing / HS Code / Payment Terms / Exchange Rate 全无 → 外销订单无法表达贸易条款，只能靠 PI（但 PI 也未含这些字段）。
5. **闭环校验与数据脱节**：代码 `deal-flow` 强制"合同/PI CONFIRMED 才可建订单"，但生产 orders 的 `contractId`/`piId` 全 0 → **强制门未在生产生效**，订单直建。要么是功能上线前旧数据，要么是校验未真正触发。
6. **Opportunity 无 salesType 也无技术参数**（前轮已证）：作为"双体系共同项目主实体"目前不成立——它既不承载域，也不承载技术需求。

## 8. 架构判断

**结论：HOLANG 未来更适合「一个 CRM 两套流程」，而非两套独立 CRM。**

代码层依据：
1. **单一客户主档**：`Customer` 是**一张表**，通过 `salesType` + `businessLine` 双标签区分内外销，而非两个客户库。生产数据 0 例跨域重名，说明当前就是用"单池 + 标签"在跑。
2. **共享下游履约**：Delivery / Invoice / Payment 共用同一套模型，仅经订单的 salesType 继承域。若拆两套 CRM，这些会严重重复。
3. **域由角色派生 + 中间件强制**：`deriveSalesType` + `enforceSalesTypeScope` 是统一的"单系统多域"范式，不是"双系统"。
4. **Contract 与 PI 是同一 Order 模型上的两个可选前件**（`contractId` / `piId`），证明设计者意图是"同一订单流程，按域走不同前置单据"，而非两套订单。

**不是"两套完全独立 CRM"**：会破坏统一客户池、重复履约模块、割裂业绩统计，与现有 schema 和代码范式冲突。

**也不是"当前证据不足"**：代码已明确编码双流程（合同/PI 互斥门、salesType 透传、角色域树），且有生产数据证明双域都在真实使用。证据充足。

**待办（不开发，仅记录）**：在动手销售 V1 数据模型前，必须先用 §7 的 10 个问题向业务确认，尤其是 Q1（客户主档共享策略）与 Q3（PI 边界）——这二者直接决定 Customer / Order / Pi 模型怎么改。
