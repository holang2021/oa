## 一、三方共识（已清晰，可直接进蓝图）

1. **落地平台 = 自建 OA（holang-oa, TS/Node/Prisma），OA 是唯一 SoR**；伙伴云降为待迁入数据源（CRM + 售后宝 搬进 OA）。
2. **外销参考询盘云**：Marketing + 外销融合；线索统一池（`Lead` 表 + `salesType=EXTERNAL`）；来源归因字段（utm*/landingPage）加在 `Lead`；新建 `marketing_campaigns` 做 活动→线索→商机→回款 归因链。
3. **统一文件模板由 OA 代码生成**（docx/pdf 模板引擎）：同一份订单/商机数据自动生成 PI / PL / 销售合同 / 内销商务合同；关键字段（币种/数量/金额/税号/贸易条款）**跨文件一致性校验、缺字段禁导出** → 防错核心（承接刘总"防模板出错"诉求）。
4. **售后 MVP = 服务请求 + 处理进度 + 知识沉淀**（基于伙伴云「售后宝」形态，利他导向：进度透明、知识反哺新人、客户历史一眼可见）；二期补充 **售后报价 / 售后合同 / 质保计费** 三关联。
5. **RBAC 在企微自建应用（HOLANG管理 1000081）**：角色清单 = 销售员 / 主管 / 内销 / 外销 / 售后 / 市场 / 财务对账 / 管理员；身份源 = 企微通讯录部门标签（`wecom_departments` 已存在）；`User.wecomUserId` 做锚点。
6. **伙伴云迁移**：按 `huobanId` 映射 upsert；OA 已有表（customers/contacts/leads/opportunities/quotes/orders/contracts/payments/invoices/deliveries/follow_ups/contract_entities）直接承接，售后模块新建；执行时先做字段口径对齐 + 脏数据清洗。
7. **前瞻性 / 不换 Java**：OA 本就 TS/Node，刘总"不用 Java/Python 以免过时"已满足；保持 tech-lead 已定严格分层架构（Express + 分层 + Prisma/zod/TS），对接 SRM/仓库/财务/技术做成标准接口契约而非硬编码。

## 三、已定前瞻性硬约束（刘总定调，直接进蓝图，无需再确认）

> **H-1 多端运行权力保留**（2026-07-22）：新建系统须保留未来转 **APP / 小程序 / 网页端** 三种形态运行的权力，不被锁死在单一网页端。

- **治理解读**：与刘总早前"不用 Java/Python、避免平台锁定、保持前瞻性"一脉相承。OA 现为本栈 TS/Node（前端 TS），天然支撑网页端；要保留转 APP / 小程序，必须在架构上做到——① 业务层（service/repository/API）与展示层**解耦**，API 优先且标准化（BFF 或标准 REST/GraphQL 契约）；② 前端避免绑定单一 Web 框架导致无法跨端；③ 数据主权在我、接口标准化，为多端共用打底。
- **与企微自建应用的关系**：企微自建应用（HOLANG管理 1000081）天然可在企微内承载小程序 / H5，APP 形态可走企微或独立壳；这也是 RBAC 在企微落地后自然支持多端的入口。
- **进蓝图要求**：tech-lead 在《OA 自建落地蓝图 v1》中必须单列"多端适配架构"小节，给出前端与业务解耦方案 + 多端技术路线（自建原生壳 / 企微小程序 / 跨端框架 TS 生态），作为硬约束而非可选。
