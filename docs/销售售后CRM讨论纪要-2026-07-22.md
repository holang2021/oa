## 一、三方共识（已清晰，可直接进蓝图）

1. **落地平台 = 伙伴云低代码**：三方一致接受，满足"拖拽搭建、后续不改代码"约束。
2. **外销参考询盘云**：Marketing + 外销业务融合，线索统一池，来源渠道 / 关键词 / 内容触点可归因到回款。
3. **统一文件模板防错机制**：PI / PL / 销售合同 / 内销商务合同，均由"同一份订单 / 商机数据**自动生成**"而非手工新建；关键字段（币种 / 数量 / 金额 / 税号）做**跨文件一致性校验，缺字段不允许导出** → 这是刘总"防模板出错"诉求的核心落地方式。
4. **售后轻量化 MVP = 服务请求 + 处理进度 + 知识沉淀**：利他导向 = 进度透明、知识反哺新人、客户历史一眼可见；暂不做复杂 SLA / 备件计费。
5. **角色权限用 RBAC，在企微上以"角色"定义**：身份源 = 企微通讯录部门 / 标签（已有 `wecom_departments` 表支撑）。
6. **复用 OA 已有数据模型**（customers / orders / quotes / contracts / payments），减少重复建设；**数据主权留我方**（开放 API / 可导出），规避平台锁定。

## 三、⚠️ 吃不准清单（须刘总确认）

1. **平台 / SoR 关系（最关键）**：伙伴云是否取代 OA 成为系统记录源(SoR)？还是 OA 续任 SoR、伙伴云做薄层？此前 Phase 1 蓝图（OA 自建 TS/Node）是否作废？
   - **治理注**：OA schema 已预埋 `huobanId`（唯一）字段，说明上一版架构本就规划与伙伴云打通，**非推倒重来**；建议伙伴云为新业务 SoR，OA 历史数据经 `huobanId` 映射迁移 / 只读对接。
2. **统一模板审批权 / 版本唯一性**：PI/PL/合同最终定版归谁？销售拟 → 财务 / 法务审 → 刘总终审？英文合同是否需外部律师背书？
3. **内外销流程**：共用一套以 `salesType` 分支，还是两套独立流？
4. **售后 MVP 边界**：工单是否关联回款 / 质保计费？利他知识卡由谁维护？
5. **角色权限与企微**：角色映射 HOLANG管理(1000081) 的双向同步机制；管理员 / 财务对账等角色清单确认。
6. **伙伴云能力边界**（tech-lead 评估项，需刘总知会）：开放 API 限额、多币种汇率来源、GEO 外部数据对接可行性——直接影响前瞻性与后续 SRM / 仓库 / 财务 / 技术对接。

## 四、治理提示：对"不用 Java/Python"的再解读

刘总"不用 Java/Python 写程序代码以免过时"的意图 = **避免技术债 / 厂商绑定 / 难维护**。伙伴云低代码已满足"不写代码"；但**真正的前瞻性风险转为"平台生命周期 + 厂商锁定"**。治理要求写入落地蓝图硬性约束：
- 业务规则落平台配置 + 标准数据流，避免平台专属脚本深定制；
- 坚持数据主权（可导出 / 开放 API）；
- 与 SRM / 仓库 / 财务 / 技术的对接做成**标准接口契约**，而非硬编码。
