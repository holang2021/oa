## 二、事实核查（关键更正）

- ⚠️ **此前记录失真**：2026-07-21 的《数字化角色协同架构》与项目记忆均记载 `holang-tech-lead`「已建并注册 v1.0.0」。**经全盘核实，该专家此前并未真正注册成功**——注册目录里只有 6 个专家（brand-growth / digital-product-owner / exploration / gas-sales / governance / product-rd），无 tech-lead。也就是说，刘总昨天见的"落地角色"是**临时拉起的 agent/skill，不是常驻专家**。
- 这恰好印证了刘总的痛点：**干活的人不是常驻实体 → 规划会没他 → 可行性方案是空中楼阁**。
- 本次已正式创建 `holang-tech-lead` 专家（agent 型，categoryId=02-Engineering），并赋予「建设落地负责人」责任。

## 三、治理结论（逐条回答）

### Q1：落地角色 = 信息化总监 ✅ 已升级为专家
- **确认**：你描述的画像（PM 前瞻 + 懂代码 + 对落地负责）正对应「信息化总监」职责定位（公司 IT 系统规划 / 技术蓝图 / 代码规则 / review / 验收）。
- **升级动作**：因该专家此前从未真正落地，本次 = 正式**创建** holang-tech-lead 专家（v1.0.0 已注册，头像已生成，WorkBuddy 面板可见），并新增两项责任：
  1. **建设落地 accountability**：所有建设规划的强制到场方；对落地负责（驱动排期、跟踪依赖、review 阶段产出、在验收栏签字）。落地角色缺席时，方案只能叫「规划草稿（待落地方会签）」，不得称「可行性方案」。
  2. **选型对标**：建设前主动调研并对标成熟外部系统。
- **边界澄清**：信息化总监**不亲手写码/部署**（写码交 CodeBuddy、部署交人类技术方，受服务器禁令约束）。"对落地负责" = 驱动 + 审查 + 验收签字，不是下键盘。

### Q2：外销 CRM 参考询盘云 + 外销兼 marketing 运营
- **询盘云已在设计中被引用**：`system_design.md` 等 8 篇文档已将「询盘云」列为外销 CRM 设计参考，本次只是**显式归属**到选型对标职责。
- **归属**：参考询盘云这类外部对标 = holang-tech-lead 的「选型对标」职责产出，输入给外销 CRM 蓝图。
- **外销兼 marketing 运营 → holang-brand-growth（市场增长专家）必须在场**：上一轮 CRM 规划已确认其全程参与；外销本就重获客轻品牌、兼 marketing 运营，销售 + 市场两视角共同提供需求，由 tech-lead 综合成蓝图。

### Q3：ERP 等后续系统的"外部成熟系统查询借用"谁做
- **Owner = holang-tech-lead（建设落地负责人）的「选型对标」常驻职责**。每次建设前必做：
  1. 内部复用闸门（六层：HOLANG 已有 → WorkBuddy 专家 → Skill → Workflow → 改造复用 → 新建），OA 已有不重建；
  2. 外部选型对标（调研询盘云/成熟 ERP 等，输出「可借鉴 / 可复用 / 自研」三栏结论）。
- **新增运行资产「选型对标知识库」**：记录每次对标了哪些外部系统、可借鉴点、是否复用，跨项目沉淀，避免重复调研。
- **新增治理硬规则（建设前强制 gate）**：未跑「内部复用 + 外部对标」不得出蓝图；落地角色缺席不得称可行性方案。
