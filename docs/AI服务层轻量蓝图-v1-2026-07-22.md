## 〇、一句话结论（给刘总）

**现在不写、不起 AI 服务。** 当下所有 AI 价值用 WorkBuddy 的「AI 数字员工（专家/技能/Agent）」承载；本蓝图把"将来规模化时那个独立 AI 服务"的**边界、接口、选型**先定死，避免日后临时起服务时破坏双实例隔离、重复造 IMA/WorkBuddy 轮子。

**为什么（逐条）：**
1. 当前 AI 用法零散（DeepSeek/WorkBuddy 对话、IMA 知识库、WorkBuddy 专家/Agent），**价值没问题，缺的是"统一服务"**——但这点是"规模化痛点"，不是"首版阻塞痛点"。
2. 真要起服务，必须保证**双实例 `salesType` 隔离延伸到 AI 调用**、客户资料不出境、不碰核心交易——这些约束现在没人验证，硬起服务反而污染 Phase 1。
3. WorkBuddy 数字员工已能跑通"询盘分类""知识问答"原型，**用零边际成本验证业务价值**，等触发条件到了再"固化"成 Python 服务，风险最低、浪费最少。

**边界（本角色不做）：** ❌ 不写 FastAPI 代码；❌ 不起服务/下部署指令；❌ 不替业务拍 AI 判定规则。

## 一、边界划分（AI 服务做什么 vs TS 核心保留什么）

> 核心原则：**AI 服务是"能力层"，不是"业务系统"。它不拥有数据、不拥有交易、不拥有权限，只对外提供"AI 函数"。** 所有 CRUD/鉴权/主数据/审批/业务规则留在 TS 核心（3001），严禁外溢。

### 1.1 AI 服务做（职责边界内）
| 能力 | 说明 | 形态 |
|------|------|------|
| **RAG 知识问答** | 基于 HOLANG 产品/政策/话术知识库回答员工/客户问题 | 内部 API + 可选前端浮窗 |
| **询盘→AI 分类→写 CRM** | 接收原始询盘文本，输出结构化字段（客户名/国家/渠道/意向产品/优先级），由 TS 核心落库 | 内部 API（AI 只产出"草稿"，落库权在 TS） |
| **报价辅助** | 根据产品/数量/国别，给参考价区间、运费/关税提示、利润率预警（**不给最终价**） | 内部 API（建议值，人审） |
| **内容生成** | 邮件/WhatsApp 跟进话术、社媒文案、产品介绍中英文稿 | 内部 API |
| **客户意图识别** | 从跟进记录/邮件流识别客户阶段与风险信号，回写标签（**由 TS 落库**） | 内部 API |

### 1.2 TS 核心保留（AI 服务不碰）
- CRUD、鉴权（JWT/`salesDomain` 强制）、业务规则、主数据（`customers`/`orders`/`payments`…）、审批流。
- 所有"写库"动作：AI 服务**只返回结构化建议**，落库必须由 3001 的 controller→service→repository 完成（复用 Phase1 分层契约）。

### 1.3 「不做」清单（边界红线）
- ❌ **不碰核心交易**：AI 服务无订单/回款/审批的写权限，不能直接改 `orders`/`payments`/`approvals`。
- ❌ **不存业务主数据**：AI 服务**不承载** `customers`/`leads`/`orders` 等主数据；向量库只存"知识文档切片"与"对话缓存"，可随时重建。
- ❌ **不持有鉴权态**：AI 服务不解析用户业务权限，只认"内部 service token"；业务域（`salesType`）由调用方（3001）透传，AI 服务只做"按域隔离检索"，不二次鉴权。
- ❌ **不替代 CRM/ERP**：它是挂在 3001 旁边的"智力插件"，不是第二套系统。
- ❌ **不引入除 LLM+向量库外的重依赖**（不引消息队列/工作流引擎作 Phase 1 标配）。

## 二、接口契约（TS 后端 3001 → AI 服务）

> 约定：
> - AI 服务默认基址 `http://localhost:8000`（FastAPI 默认，端口与 3001 隔离，**独立进程**）。
> - **所有端点强制 `salesType` 透传**（双实例隔离延伸到 AI 调用）——缺省/非法值一律 400 拒绝。
> - 鉴权：内部 **service token**（`X-Service-Token: <secret>`，由 3001 持有，AI 服务校验；不暴露给前端）。
> - 统一响应结构 `{ code, message, data }`（与 3001 的 `utils/response.ts` 一致），`code:0`=成功。
> - **同步/异步取舍**：分类/问答/意图识别属"请求-响应"**同步**（AI 内部可带超时与降级）；长任务（批量内容生成、知识库重建索引）走**异步 + 任务轮询**，不在首版强制。

### 2.1 询盘自动分类 → 写 CRM
```
POST /api/ai/classify-lead
Headers: X-Service-Token: <secret>, Content-Type: application/json
Body:
{
  "salesType": "EXTERNAL",            // 必填，透传
  "rawText": "Hi, we need a 99.9% nitrogen generator for food packaging...",
  "source": "官网" | "展会" | "社媒" | "代理" | "海关",  // 可选
  "locale": "en" | "zh"               // 可选，默认 en
}
Response 200:
{
  "code": 0,
  "message": "ok",
  "data": {
    "customerName": "ABC Foods Ltd.",
    "contactName": "John",
    "email": "john@abcfoods.com",
    "country": "United States",
    "region": "北美",
    "intentProduct": "制氮机",
    "intentSpec": "99.9% 纯度 / 食品包装",
    "priority": "HIGH" | "MEDIUM" | "LOW",
    "suggestedOwnerRole": "SALES",
    "confidence": 0.91,
    "needHumanReview": false          // 低置信或歧义时 true，交人工
  }
}
```
- **落库规则**：3001 收到 `data` 后，调自身 `POST /leads`（Phase1 B2 已规划）写库，**继承 customer 的 salesType**，AI 不直接写。
- **边界**：AI 只产出"草稿 + confidence"；`needHumanReview=true` 时 3001 必须进人工确认，不自动落库。

### 2.2 RAG 知识库问答
```
POST /api/ai/rag-query
Headers: X-Service-Token: <secret>
Body:
{
  "salesType": "EXTERNAL",            // 必填，决定检索哪个知识域
  "question": "制氧机出口到德国的认证要求？",
  "topK": 5,                          // 可选，默认 5
  "locale": "zh"                      // 可选
}
Response 200:
{
  "code": 0,
  "message": "ok",
  "data": {
    "answer": "德国出口需 CE + PED 认证，建议...",
    "sources": [                      // 可追溯，防幻觉
      { "docId": "kb-0123", "title": "欧盟压力容器指令 PED", "snippet": "..." , "score": 0.87 }
    ],
    "confidence": 0.84
  }
}
```
- **为什么按 salesType 分域**：内销（工业气体）与外销（设备出口）知识库内容不同，混检会答非所问；域隔离在检索层强制。

### 2.3 报价辅助
```
POST /api/ai/quote-assist
Headers: X-Service-Token: <secret>
Body:
{
  "salesType": "EXTERNAL",
  "productId": "p-xxx",
  "quantity": 2,
  "destinationCountry": "Germany",
  "incoterm": "FOB" | "CIF"           // 可选
}
Response 200:
{
  "code": 0,
  "message": "ok",
  "data": {
    "suggestedUnitPriceRange": { "low": 12000, "high": 15000, "currency": "USD" },
    "freightHint": "海运至汉堡约 $800/台",
    "dutyHint": "德国关税约 0%（自贸协定）",
    "marginWarning": "若成交价 < 11000 则毛利率低于 15%",
    "confidence": 0.78
  }
}
```
- **边界**：返回"区间 + 提示 + 预警"，**不返回最终报价**；3001 落 Quote 时由人审，AI 不写 `quotes` 表。

### 2.4 客户意图识别（回写标签）
```
POST /api/ai/intent-detect
Headers: X-Service-Token: <secret>
Body:
{
  "salesType": "EXTERNAL",
  "customerId": "c-xxx",
  "recentTexts": ["邮件正文1", "WhatsApp记录2", ...]   // 由 3001 从 follow_ups 聚合后传入
}
Response 200:
{
  "code": 0,
  "message": "ok",
  "data": {
    "stageHint": "报价中" | "跟进中" | "成交" | "丢单风险",
    "riskSignals": ["30天无回复", "反复比价"],
    "nextActionHint": "建议 3 日内发送 PI 草案",
    "confidence": 0.82
  }
}
```
- **落库规则**：3001 收到后**可选**回写 `opportunities.stage` 或打标签，但必须经人审/有权限校验，AI 不直写。

### 2.5 内容生成
```
POST /api/ai/content-generate
Headers: X-Service-Token: <secret>
Body:
{
  "salesType": "EXTERNAL",
  "type": "EMAIL" | "WHATSAPP" | "SOCIAL" | "PRODUCT_DESC",
  "context": { "customerName": "...", "product": "制氮机", "tone": "专业" , "locale": "en" },
  "async": false                       // 长稿可 true 走异步
}
Response 200:
{ "code": 0, "message": "ok", "data": { "content": "Dear John, ..." , "confidence": 0.9 } }
```

### 2.6 鉴权与调用方式小结
- **内部 service token**：3001 持有密钥，AI 服务中间件校验；前端**永远不直接调 AI 服务**（经 3001 中转，保证 `salesType` 由服务端 `salesDomain` 强制覆盖，防越权——与 Phase1 §1.3 一致）。
- **salesType 透传**：AI 服务每个端点都校验 `salesType ∈ {EXTERNAL, INTERNAL}`，缺失即 400；检索/分类按域隔离。
- **降级**：LLM 超时/不可用时，AI 服务返回 `code≠0` + `needHumanReview=true`，3001 退回人工流程，**不阻断主业务**。

## 三、技术选型（为什么 Python，但隔离部署）

### 3.1 选型结论
| 项 | 选择 | 为什么 |
|----|------|--------|
| 语言/框架 | **Python + FastAPI** | Python 是 LLM/RAG/向量检索生态最成熟（LangChain、Sentence-Transformers、OpenAI/DeepSeek SDK、Chroma/Qdrant/FAISS 一等公民）；FastAPI 异步、类型化、自动 OpenAPI 文档，工程化足够。 |
| 向量库 | **轻量起步 Chroma（本地文件）**，规模化切 Qdrant | Chroma 零运维、单进程可跑，首版够用；QPS 超阈值再上 Qdrant（独立部署、可水平扩展）。 |
| 编排 | **首版不引 LangChain**；仅用 SDK 直调 + 自写检索函数 | LangChain 抽象重、调试黑盒；HOLANG 场景简单（分类/检索/生成），自写 200 行内函数更可控、易维护。触发复杂多步 Agent 再评估。 |
| LLM | **DeepSeek（主）+ 可选 Claude/通义** | 老板已用 DeepSeek；成本优；客户资料不出境需选合规部署（见风险 §6.3）。 |
| 部署 | **独立进程 + 独立端口（8000），与 3001 物理隔离** | 核心不被 Python 依赖污染；Node 崩不影响 AI，AI 崩不影响 CRM。 |

### 3.2 为什么 Python 但必须隔离（关键判断）
- **为什么 Python**：AI 生态碾压 TS（embedding、RAG、微调、Agent 框架），强行用 TS 重写 AI 层 = 重复造轮子 + 生态劣势。
- **为什么隔离部署（不混进 3001）**：
  1. **核心栈不换**是老板红线（§选型规范 v1）——AI 服务的 Python 依赖（torch/transformers）若进 Node 工程会污染核心、拖累构建、招人割裂。
  2. **故障隔离**：LLM 调用慢/贵/偶发 5xx，不能拖垮 CRM 主链路；独立进程 + service token 网关让 AI 可随时降级。
  3. **演进自由**：未来 AI 服务可独立扩副本、换模型、上加 GPU 机器，不动 3001 一行代码。
- **边界**：❌ AI 服务不读 3001 的 SQLite/Prisma；❌ 不共享 Node 进程；❌ 不引入到前端构建链。

### 3.3 轻量起步配置（交给 CodeBuddy 的未来实现参考，非现在开发）
```
ai-service/                # 独立仓库/独立目录，不进 holang-oa
  main.py                  # FastAPI app + 路由
  routers/ai_*.py          # 对应 §2 各端点
  core/security.py         # X-Service-Token 校验 + salesType 校验
  services/rag.py          # 检索 + 生成
  services/classify.py     # 询盘分类
  store/chroma_client.py   # 向量库客户端
  config.py                # 端口/密钥/模型名（env 注入）
  requirements.txt         # fastapi, uvicorn, chromadb, openai, pydantic
```
- **验收门槛（未来）**：所有端点缺 `salesType` 返回 400；`X-Service-Token` 错返回 401；LLM 超时返回降级结构。

## 四、首批迁移清单（先迁哪两项，及优先级/依赖/验收）

> 判定口径：**价值高 × 已具备原型 × 不碰核心交易** 的优先。IMA/WorkBuddy 已部分具备"知识问答"与"分类"能力，迁移成本最低。

| 序号 | 能力 | 优先级 | 依赖 | 验收点 | 交给谁（未来） |
|------|------|--------|------|--------|----------------|
| **M1** | **询盘自动分类→CRM** | P0（首批） | §2.1 契约 + 3001 的 `POST /leads`（Phase1 B2） | 原始英文询盘 → 结构化字段 → 经 3001 落 `leads` 且带正确 `salesType`；低置信进人工；闭环≥20 条真实询盘准确率≥85% | CodeBuddy 写 / 人类部署 |
| **M2** | **RAG 知识库问答** | P0（首批） | §2.2 契约 + Chroma 知识库（首批灌 HOLANG 产品册/认证/FAQ） | `salesType` 分域检索；答案带 `sources` 可追溯；知识库可重建；≥50 条测试问题命中率≥80% | CodeBuddy 写 / 人类部署 |
| M3 | 报价辅助 | P1（二批） | M1/M2 之后 + `products` 主数据只读接口 | 返回区间/运费/毛利预警，不写 `quotes` | CodeBuddy |
| M4 | 客户意图识别 | P1（二批） | `follow_ups` 聚合接口 + M2 | 输出 stage/risk 提示，回写经人审 | CodeBuddy |
| M5 | 内容生成 | P2（三批） | M2 之后 | 中英邮件/WhatsApp 话术可用 | CodeBuddy |

**为什么首批只迁 M1+M2：**
- M1 直接喂饱 Phase1 的 `leads` 缺口（当前 lead 无写接口、询盘靠人工），价值最显、依赖最少。
- M2 复用 IMA/WorkBuddy 已有知识库内容，迁移=把"对话式能力"固化为"可调用 API"，不重复造知识。
- M3~M5 都依赖主数据/跟进数据就绪，**且涉及"给建议"需人审闭环**，放二/三批更稳。

## 五、当下 vs 未来边界（重要：何时该起这个服务）

### 5.1 当下交付路径（不走 Python）
- **所有 AI 价值现在用 WorkBuddy 的 AI 数字员工（专家/技能/Agent）承载**：询盘分类、知识问答、内容生成，先在 WorkBuddy 里跑通原型、验证业务、沉淀 prompt/知识。
- **本 Python 服务 = 规模化固化路径**，不是 Phase 1 交付物，**不阻塞 Phase 1、不立即开发**。
- 当下 AI 交付归属：WorkBuddy 数字员工配置 → **刘总/运营团队（业务侧）**；prompt 与知识整理 → **刘总拍业务内容**。

### 5.2 触发"起 Python 服务"的条件（满足任一即立项）
1. **RAG 查询 QPS 超阈值**：WorkBuddy/IMA 无法支撑并发或需嵌到 CRM 界面实时调用（如官网/外销站内置问答）。
2. **需生产级 SLA**：AI 能力要进客户可见链路（官网 chatbot、外销站自动回复），要求稳定鉴权、降级、监控、版本管理——数字员工形态达不到。
3. **多系统共用 AI 能力**：内销+外销+官网都要同一套分类/问答，需统一服务而非各自 WorkBuddy 实例，否则逻辑分裂、域隔离难保证。
4. **成本/合规可控性要求**：需统一计费、统一出境合规（客户资料不出境）、统一审计——独立服务是唯一可控形态。
5. **未触发前**：一律先用 WorkBuddy 数字员工，**不起服务、不写 FastAPI 代码**。

### 5.3 边界重申
- ❌ 本蓝图**不授权**现在起 8000 端口服务；❌ 不授权 CodeBuddy 现在写 AI 服务代码（M1/M2 代码等触发条件到了再排期）。
- ✅ 本蓝图授权的是"把边界/契约/选型先定死"，让未来触发时**零返工**接入，且不破坏双实例隔离。

## 六、风险

| 风险 | 说明 | 缓解（写进验收） |
|------|------|------------------|
| **R1 双实例隔离未延伸到 AI** | AI 服务若不分 `salesType` 检索/分类，内销知识答外销、外销询盘错分域 | 每个端点强制 `salesType` 校验（§2.6）；检索按域隔离；缺省 400。AI 服务无业务鉴权，域由 3001 服务端强制透传（同 Phase1 §1.3）。 |
| **R2 LLM 成本与延迟** | 每次询盘/问答都调 LLM，费用随量上涨；响应慢拖主链路 | 异步+超时降级；命中缓存（同问复用）；降级返回 `needHumanReview`；未来按 QPS 做预算阈值告警。 |
| **R3 数据隐私（客户资料不出境）** | 询盘含客户名/邮箱/国家，传 LLM 有出境风险 | 选合规部署的 DeepSeek/国内模型；**PII 脱敏**后再送模型（如邮箱掩码）；向量库只存知识文档，不存客户主数据（§1.3）。 |
| **R4 与 IMA/WorkBuddy 重复造** | 起服务后若又把 IMA 知识库搬一份，维护双份 | M2 知识库以"单一来源"为准（IMA/文档优先），AI 服务只做检索 API 封装，不另起知识库；明确"AI 服务≠知识库"，是知识库的"调用层"。 |
| **R5 幻觉/误判落库** | 分类/意图识别错 → 错分客户/错改 stage | 所有 AI 输出带 `confidence`+`needHumanReview`；低置信/歧义一律人工确认，AI 不直接写主数据（§2.1/§2.4）。 |
| **R6 污染核心栈** | Python 依赖混进 Node 工程 | 独立进程/独立仓库/独立端口（§3.2）；CI 不共享；人类技术方独立部署。 |

## 八、最大技术风险（提示）

1. **R1（隔离未延伸）最高**：若 AI 服务起的时候忘了 `salesType` 透传，等于在"统一池 + 双系统"红线上开新口子。对策：契约层把 `salesType` 列为必填（§2），验收机检"缺省即 400"。
2. **R4（重复造 IMA）次高**：起服务最易犯的错是把 IMA 知识库再搬一份。对策：明文"AI 服务是知识库调用层，不是第二知识库"（§6 R4）。
3. **时机风险**：没到触发条件就起服务 = 浪费 + 污染核心。对策：§5.2 写死触发条件，未触发不起。
