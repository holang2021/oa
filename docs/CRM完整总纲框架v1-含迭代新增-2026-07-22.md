## 系统命名与顶层设计理念（All In One）

- **系统命名**：整个 OA 系统定名为 **「All In One」**。
- **顶层设计理念（刘总 2026-07-22 14:19 定调）**：
  1. **所有事情都在系统上跑**——业务、流程、数据、沟通、协作尽量收敛到系统内，减少线下 / 多系统切换。
  2. **帮助员工快速解决问题**——系统要主动赋能，而非只是记录。
  3. **不要成为员工的负担**——流程要轻、交互要简、少必填、少卡点；能用 AI / 自动化替员工做的，不让员工手动做。
  4. **把工作顺利、简单、高效地完成**——一个入口、少切换、跨模块穿透。
- **治理含义**：本理念是**所有模块设计的顶层约束**——任何功能设计都要先问"这帮员工省事了吗？还是添负担了？"。后续总纲 v1 / 流程图 / 蓝图的审视，均以本理念为基准（第十节为多方会议审视结论）。
- **与既有硬约束一致**：H-1 多端（一个账号多端打通）、H-2 防下载（利他不泄漏）、利他导向售后，均服务于本理念。

## 〇、复用闸门约定（治理判定的基础）

- **A 直接复用**：OA 已有表 + 数据，零重建（customers/orders/payments/invoices/deliveries/contracts 等真实数据）。
- **B 改造复用**：OA 有表但字段/逻辑不足，补字段或接已有引擎（approval-engine / 模板引擎）。
- **C 新建**：OA 无对应表，需新建（售后、财务子模块、分析、生产、AI 层等）。
- 落地可行性 = 在 OA（TS/Node/Prisma）现状下能否实现，**全总纲判定为"可行"，无不可行项**。

## 四、跨模块硬约束（全部进蓝图，非可选）

1. **H-1 多端运行权力保留**：网页/小程序/APP 三形态不锁死；业务层与展示层解耦、API 优先标准化。
2. **RBAC 在企微自建应用（1000081）**：角色=销售员/主管/内销/外销/售后/市场/财务对账/管理员；身份源=企微通讯录(`wecom_departments`)。
3. **SoR = 自建 OA**：伙伴云仅临时源、内容迁入；各表 `huobanId` 迁移键。
4. **数据主权在我**：可导出/开放 API，规避平台锁定。
5. **字段级合规**：audit_log 异动、查重(国内工商·统一信用代码唯一键 / 海外邓白氏码 + DeepSeek 辅助补全/背调)、员工背调(DeepSeek API)、线索公海/回流/总监审批、报价合同发货审批流接 approval-engine、设备主数据——随批次落。
6. **统一文件模板防错**：同一份数据自动生成 PI/PL/合同，跨文件强校验、缺字段禁导出。
7. **公海绝对隔离（内销/外销）**：线索公海、客户·商机公海 一律按 `salesType` 服务端强制隔离——内销只看内销、外销只看外销，越权查询在服务端拦截（复用 Phase1 蓝图 B1 服务端域强制）；员工仅可认领/查看，禁止任何导出/下载/批量抓取。
8. **H-2 数据防泄漏**：公海及客户主数据禁止员工下载/导出（RBAC 中"导出"权限仅管理员/财务对账持有）；任何访问/认领/变更落 audit_log；与 H-1 多端并用——多端可看不可下。
9. **H-3 自动化边界红线（渐进式授权 · 刘总 2026-07-22 16:17 拍板）**：数字员工/AI 按"读 → 写 → 决"三档渐进授权——**阶段0（当前 / 运行初期）仅可读取数据**，不参与写入 / 预填 / 提醒触达 / 审批动作，业务数据一律由人操作产生；**阶段1（系统运行稳定后）放开填写 / 录入权**（代填表单、生成草稿、落库，关键节点仍须人确认 + audit_log 全留痕）；**阶段2（远期，基本不放开）审批 / 签署 / 回款确认等决策权不授予数字员工**——审批终审、合同签署、回款确认必须人工拍板（全自动禁区）。任何阶段 AI 动作须落 audit_log（复用 H-2 留痕机制）。与 7 项共识 #3「工作流内嵌 AI 自动填充」的 reconcile：阶段0 仅提示 / 读取，阶段1 起方可代填（人确认后写入）。详见第十节。
10. **H-4 客户聚合根（2026-07-22 刘总 14:55 定）**：Customer 为聚合根，其下联系人/商机/报价/合同/订单/回款/开票/售后/跟进/异动等从属实体**全部随客户实体整体移动**（移交/退公海/分配均整体带出），不单独分离、不拆分存储。离职移交/公海分配 = 移动客户聚合整体。与"统一客户池(主数据一份)"架构裁定一致。

### 1. 查重权威键（对第八节升级）
- **国内**：接**工商数据**，以「公司名称 + 统一社会信用代码」录入，但**因公司名称会变更，统一信用代码为唯一标准**（名称变、代码不变，查重以代码为准）。
- **海外**：以**邓白氏码（DUNS）**为唯一标准。
- 两域均有**公司信息变更**功能（变更走流程 + audit_log，不改权威键）。
- **DeepSeek 定位=辅助**：名称归一、代码缺失时模糊匹配、公司信息补全、变更建议；**权威键与权威源是信用代码/邓白氏码/工商数据**，不倒置。

### 2. 公海设计（含「客户公海 vs 商机公海」评估结论）
刘总提问：客户公海是否可与商机公海共用一个？治理评估结论如下。

**评估 → 建议共用一套公海机制、底层分实体。** 理由：
- 统一客户池(SoR) 已是「一份公司主数据」（按信用代码/DUNS 唯一），本身就是"客户"归属地；"客户公海"本质是**无主客户账号**（unowned account）。
- "商机公海"是**无主商机**（unowned opportunity，挂在某客户下）。
- 二者实体不同（account vs deal），但**认领/退回/再分配规则完全一致**——共用一套公海引擎（claim/return/assign/pool 状态位）可减少重复建设，符合"利他/轻量"哲学。
- 故设计：**一个公海机制 + 两类条目（客户类 / 商机体）**，公海视图按类型筛选；线索公海因实体更早（pre-customer）保持独立。

**落地结构**：
- **线索公海（独立）**：`leads` 表 + pool 状态位（unassigned/returned）+ 分配/回流/总监审批。
- **客户·商机公海（共用机制）**：`customers`(无主账号 owner_id 空) + `opportunities`(无主商机 owner_id 空)，共享 claim/return 规则；视图按「客户/商机」类型切换。
- 三者公海归属统一用 `in_public_pool` 标志 + `pool_type`（lead/customer/opportunity）。

### 3. 内销/外销 绝对边界（硬约束 · 复用 Phase1 B1）
- 线索公海、客户·商机公海 **一律按 `salesType` 服务端强制隔离**：内销员工只见内销公海、外销员工只见外销公海，零交叉。
- 越权查询在**服务端拦截**（复用 Phase1 蓝图 B1「服务端域强制」——双实例隔离红线首件），前端切 URL/改参数均无效。
- 双运营系统（外销/内销分支）同样受此隔离约束，与公海同源。

### 4. 数据防下载（H-2 硬约束）
- 公海数据及客户主数据：**员工禁止下载 / 导出 / 批量抓取**。
- RBAC 中"导出/下载"权限**仅管理员、财务对账**持有；销售/内销/外销/市场/售后角色仅有"认领 + 在屏查看"权限。
- 任何访问、认领、变更、导出动作落 **audit_log**（谁、何时、哪条、何操作），可追溯。
- 与 H-1 多端并用：多端（网页/小程序/APP）**可看不可下**——移动端同样禁导出。

### 5. 复用闸门判定
| 能力 | 现状 | 闸门 | 备注 |
|---|---|---|---|
| 查重权威键(信用代码/DUNS) + 工商/邓白氏接入 | 无 | C | 新建；DeepSeek 辅助 |
| 公司信息变更功能（两域） | 无 | C | 变更流程 + audit_log |
| 线索公海 | `leads` 有、缺 pool 状态 | B→C | 补 pool/分配/回流/审批字段 |
| 客户·商机公海（共用机制） | 无 | C | 一套引擎 + 分实体 |
| 内销/外销 服务端隔离 | Phase1 B1 已规划 | A/B | 复用服务端域强制 |
| 数据防下载（H-2） | 无 | C | RBAC 导出权限 + audit_log |
