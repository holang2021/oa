# 建设草案：内部表单 / 打印设计器（轻量低代码）

> 状态：**DRAFT（草案，未实施、未评审、未上线）**
> 立项依据：互补分析第 1 条「立项内部表单/打印设计器」——解决"每加模块都手写 React 表单"导致的产能瓶颈（对照分析中 9 个看板 + 多张单据全缺/待建）。
> 参照：dromara/skyeye 的零代码设计器思路（仅借设计，不引入其 Java 栈）。
> 日期：2026-07-16

---

## 一、目标与边界

**目标**
- 用"表单定义（JSON Schema）+ 动态渲染"替代"每个模块手写一套 React 表单"，把新增业务表单的工期从"天级"降到"小时级"。
- 提供"打印模板"能力，让报价单/合同/发货单从数据直接生成可打印/可导出 PDF 的成品。

**边界（本期不做）**
- ❌ 不做 skyeye 式的完整零代码平台（不含流程设计器、编码设计器、布局设计器全套）。
- ❌ 不替换已有的「自建审批引擎」——审批引擎（已实现于 holang-crm）按 **方案 A** 迁至 OA 前端（holang-admin）统一承载（见 `决策记录-OA统一基线.md`）；表单设计器与之并列，表单提交后挂接审批。
- ❌ 不引入 Java/微服务栈；完全复用我们现有 Node + React 栈。
- ❌ 不覆盖 MES/WMS/EHR（那是 Phase 2/3，借 skyeye 模块设计，非本期）。

---

## 二、设计原则

1. **Schema 驱动**：表单 = 一段 JSON 定义（字段、类型、校验、布局、来源）。改表单 = 改 JSON，不碰代码。
2. **复用企微身份**：与现有系统一致，仅企微 OAuth 登录，表单数据带 `creatorUserId` / `deptId` 用于数据权限。
3. **主数据联动**：客户、产品从已有「客户管理」「产品管理」主数据下拉选择，不重复录入。
4. **渐进存储**：v1 用通用 JSON 存储（贴合我们 Phase 1-2 的 JSON/Bitable 路线），分析需求强的表单后续再做结构化镜像。
5. **栈统一**：落在 **OA 前端 `holang-admin`**（React 19 + Vite 7 + Tailwind + Radix/shadcn），作为 HOLANG OA 统一新前端，最终替代 `holang-oa/packages/oa`（决策见 `决策记录-OA统一基线.md`）。

## 三、总体架构

```
┌─────────────────────────────────────────────┐
│  表单设计器（管理端，仅管理员/系统角色可见）   │
│  可视化配置：字段、类型、校验、布局、来源      │
└───────────────┬─────────────────────────────┘
                │ 产出 form_definition (JSON)
                ▼
┌─────────────────────────────────────────────┐
│  form_definitions 存储（通用表 / JSON 字段）   │
└───────────────┬─────────────────────────────┘
                │
   ┌────────────┴─────────────┐
   ▼                          ▼
┌────────────────┐    ┌──────────────────────┐
│ DynamicForm 运行时 │    │ 打印模板引擎          │
│ 按 schema 渲染表单 │    │ HTML + 变量绑定        │
│ + zod 校验        │    │ → 浏览器打印 / PDF     │
└───────┬────────┘    └──────────┬───────────┘
        │ 提交                    │ 套用
        ▼                        ▼
┌─────────────────────────────────────────────┐
│  form_data 存储（通用表：formId + data JSON）  │
│  + creatorUserId / deptId（数据权限）          │
└─────────────────────────────────────────────┘
                │
                ▼ 可挂接
        已有「自建审批引擎」（动态组件）
```

**关键组件**
- `DynamicForm`：一个 React 组件，接收 `schema` 渲染任意表单（文本/数字/日期/单选/多选/下拉/子表/文件/关联主数据）。
- `FormRenderer` + `PrintTemplate`：同一份 `form_data` 既能填又能打印。
- 子表（table）能力：报价单明细行、合同货物明细等多行结构是刚需，必须支持。

## 四、技术选型（理由）

| 项 | 选择 | 理由 |
|----|------|------|
| 前端框架 | React 19 + Vite 7 + Tailwind + Radix/shadcn | 复用 **OA 前端 `holang-admin`** 现有栈，组件库现成 |
| 校验 | zod（已在该栈依赖中） | 与 schema 同源，类型安全 |
| 表单定义 | 自研轻量 JSON Schema（fieldType / label / rules / options / source） | 比 JSON Schema 标准更贴业务，够用即可 |
| 存储（v1） | 通用表 `form_data(form_id, data JSON, creator, dept, created_at)` | 零迁移成本，贴合当前 JSON/Bitable 路线 |
| 打印 | HTML 模板 + Mustache/Handlebars 变量绑定 → `window.print()` / 导出 PDF | 无需重引擎，浏览器原生打印 |
| 后端 | 复用 Node/Express（扩展现有 wecom-callback 或新建轻服务） | 不新增语言栈 |
| 主数据来源 | 客户管理 / 产品管理 的查询 API | 下拉 option 来自已有主数据 |

> **栈统一提醒（风险）**：当前 `holang-crm` 是 React 18，而 **OA 前端 `holang-admin`** 已是 React 19。表单设计器落地在 OA 前端；crm 侧审批引擎已按方案 A 迁至 OA 前端，迁移验证通过后清除 `holang-crm`，避免再分裂版本。

## 五、数据模型（Schema 草案）

**form_definition**
```json
{
  "formId": "quotation",
  "name": "报价单",
  "version": 1,
  "fields": [
    { "key": "quoteNo",      "label": "报价编号", "type": "text",     "auto": "rule:HQ+YYMMDD+seq", "readonly": true },
    { "key": "quoteDate",    "label": "报价日期", "type": "date",     "default": "today" },
    { "key": "validDays",    "label": "有效期",   "type": "number",   "unit": "天", "default": 30 },
    { "key": "customerId",   "label": "客户",     "type": "lookup",   "source": "crm/customer" },
    { "key": "subject",      "label": "主题",     "type": "text" },
    { "key": "items",        "label": "明细行",   "type": "table",
      "columns": [
        { "key": "productId", "label": "产品",   "type": "lookup", "source": "product" },
        { "key": "model",     "label": "型号",   "type": "text", "fromProduct": "model" },
        { "key": "flow",      "label": "流量",   "type": "text", "fromProduct": "flow" },
        { "key": "purity",    "label": "纯度",   "type": "text", "fromProduct": "purity" },
        { "key": "qty",       "label": "数量",   "type": "number" },
        { "key": "unitPrice", "label": "单价",   "type": "number", "fromProduct": "price" },
        { "key": "subtotal",  "label": "小计",   "type": "formula", "expr": "qty*unitPrice", "readonly": true }
      ]
    },
    { "key": "total",     "label": "合计",   "type": "formula", "expr": "SUM(items.subtotal)", "readonly": true },
    { "key": "totalCn",   "label": "大写",   "type": "formula", "expr": "toCnMoney(total)", "readonly": true },
    { "key": "remarks",   "label": "条款备注", "type": "richtext" }
  ]
}
```

**form_data**
```json
{ "form_id": "quotation", "data": { "quoteNo":"HQ26042105", "customerId":"...", "items":[...], "total":155600, "totalCn":"壹拾伍万伍仟陆佰元整" }, "creatorUserId":"...", "deptId":"...", "created_at":"..." }
```

> `auto` / `formula` / `fromProduct` 是三类"自动值"：编号规则、计算字段、从主数据带出规格——覆盖报价单真实需求（见下方首版字段）。

## 六、首版覆盖（3 张表单，字段取自真实业务）

### 6.1 报价单（依据 `quotation_260421.json` 真实结构）
- 头：报价编号(自动) / 报价日期 / 有效期(天) / 客户(主数据) / 我方信息(主数据) / 主题
- 明细行（子表）：产品(主数据) / 型号 / 流量 / 纯度 / 氧含量 / 进气口 / 出气口 / 功率 / 外形尺寸 / 用气需求 / 数量 / 单价 / 小计(自动)
- 合计(自动) / 大写(自动)
- 条款备注：价格说明 / 交货期 / 付款方式(30预付款·65发货款·5调试)
- 落款：我方公司 + 日期

### 6.2 合同（依据架构规划 5.4 合同管理）
- 头：合同编号(自动) / 签约日期 / 客户(主数据) / 我方 / 合同类型
- 货物明细（子表）：产品 / 规格 / 数量 / 单价 / 金额
- 金额合计(自动) / 大写(自动)
- 条款：交货期 / 付款节点 / 质保 / 违约责任 / 争议解决
- 双方签章区

### 6.3 发货单（依据架构规划 5.5 发货通知）
- 头：发货单号(自动) / 发货日期 / 客户(主数据) / 关联合同/订单号 / 收货地址 / 物流
- 发货明细（子表）：产品 / 型号 / 数量 / 实发
- 备注：随货资料 / 验收要求

> 三张表单共用同一套 `DynamicForm` + 子表 + 公式 + 打印模板机制，验证设计器的通用性后即具备横向复制能力。

## 七、与现有系统衔接

| 衔接点 | 方式 |
|--------|------|
| 登录/身份 | 复用企微 OAuth，表单数据带 `creatorUserId`/`deptId` |
| 客户/产品主数据 | `lookup` 字段 `source` 指向已有查询 API，下拉即时拉取 |
| 审批 | 表单提交后可挂接已有「自建审批引擎」（动态组件），如报价→销售经理审批 |
| 菜单入口 | 在 **OA 前端 `holang-admin`** 新增「表单中心」菜单（设计器 + 我的表单 + 待我审批） |
| 数据分析 | v1 通用 JSON 存储；后续对报价/合同做结构化镜像，喂给缺失的 9 个分析看板 |

## 八、实施步骤（最小安全动作，分步闭环）

| 步 | 动作 | 产出 | 验证 |
|----|------|------|------|
| 1 | 在 admin 栈实现 `DynamicForm` 基础字段（text/number/date/select/lookup/table/richtext） | 可渲染单张固定 schema 表单 | 手动填一张演示表单 |
| 2 | 实现 `form_definitions` + `form_data` 通用存储与保存/读取 API | 表单可持久化 | 保存后刷新不丢 |
| 3 | 实现 `auto`/`formula`/`fromProduct` 三类自动值 | 报价单编号、小计、合计、大写自动算出 | 对照 `quotation_260421.json` 数值一致 |
| 4 | 实现打印模板（Mustache + 浏览器打印），先做报价单模板 | 报价单可打印/导出 | 打印预览与现有 Excel 版式一致 |
| 5 | 接入客户/产品主数据 lookup | 下拉即时拉取 | 选客户/产品自动带出 |
| 6 | 表单中心菜单 + 提交挂接审批引擎 | 端到端可用 | 销售填报价→经理收到审批 |
| 7 | 复制出合同、发货单模板 | 三表单齐活 | 三张均可填可打 |

## 九、验收标准

- [ ] 新增一张业务表单 = 写一份 `form_definition` JSON，无需改 React 代码。
- [ ] 报价单小计/合计/大写数值与历史 `quotation_260421.json`（155600 / 壹拾伍万伍仟陆佰元整）一致。
- [ ] 报价单打印版式还原现有 Excel 报价单。
- [ ] 客户/产品下拉来自主数据，不重复录入。
- [ ] 表单提交可进入已有审批引擎。

## 十、风险与开放问题（待确认）

| # | 项 | 建议 / 待决 |
|---|----|------------|
| 1 | **存储选型**：通用 JSON vs 结构化表 | ✅ **已决（2026-07-16）**：按当下方案用本地 JSON（贴合 Phase 1-2 路线），结构化镜像留待分析看板急需时再做。 |
| 2 | **栈统一 / 清 holang-crm**：crm(React18) 与 admin(React19) 分裂 | ✅ **已决（2026-07-16，方案 A）**：以 **OA 前端 `holang-admin`(React19)** 为唯一前端基线，最终替代 `holang-oa/packages/oa`；`holang-crm` 内的审批引擎**先迁到 OA 前端再清**，不得先删（避免丢失审批能力）。`holang-crm` 其他可复用逻辑（FormField/PrintPreview/GenericListPage）在迁移验证通过后一并评估。 |
| 3 | **公式引擎范围**：v1 仅支持 `SUM`/`qty*price`/`toCnMoney` 等常见表达式，复杂计算暂不支持。 |
| 4 | **权限**：表单数据权限复用现有 `role + dataScope`，设计器仅管理员可见。 |
| 5 | **打印跨端**：企微 H5 内打印体验有限，PDF 导出为主，现场打印走 PC。 |
