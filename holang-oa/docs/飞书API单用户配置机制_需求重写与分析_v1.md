## 1. 需求重写（清晰明确版）

**原始诉求（口语）**：针对飞书 API 的配置功能，目前后台仅支持配置单个用户（即仅限我一人）的权限与参数。请说明该配置机制的具体实现方式与设计逻辑，并阐明为何当前方案在多人协作场景下显得复杂或绕弯，同时指出其在实际使用中的限制与可优化方向。

**重写为规范需求（REQ-1 ~ REQ-5）**：

> **REQ-1（配置模型）**：飞书 API 的配置采用**单租户、单身份模型**——系统只持有**刘总一人**的飞书授权（user_access_token + refresh_token），不为基础团队成员申请或分配任何飞书侧权限。所有飞书读写（知识库写入、正文读取、检索）统一以该身份进行。
>
> **REQ-2（实现说明义务）**：需书面说明该配置机制的**具体实现方式**（OAuth 授权码流程、令牌存储与续期、调用链路）与**设计逻辑**（为何选单身份而非多身份）。
>
> **REQ-3（协作场景剖析）**：需客观阐明，在**多人协作**（11 人团队、内外销并行）场景下，单身份模型为何在权限、限流、审计、溯源等维度显得**复杂或绕弯**。
>
> **REQ-4（限制列举）**：需列出该方案在**实际使用中的硬性限制**（可用性单点、额度瓶颈、细粒度权限缺失等）。
>
> **REQ-5（优化路线）**：需给出**可优化方向**（在不违背"统一身份、免成员开通"核心诉求前提下的演进路径），供未来复盘决策。

## 2. 配置机制的实现方式与设计逻辑

### 2.1 具体实现方式（规划态）

```
[一次性] 刘总在飞书开放平台给 OA 应用登记重定向 URL
        ↓
GET  /api/v1/feishu/oauth/authorize
        → 302 跳飞书 authen/v1/authorize（scope: wiki, docs, contact）
        ↓
刘总扫码/点授权 → 飞书回调
GET  /api/v1/feishu/oauth/callback?code=xxx
        → 后端用 code 换 user_access_token + refresh_token
        → refresh_token 落盘 api-configs.json（权限 600），access_token 内存缓存
        ↓
[日常] 所有飞书调用：
  Authorization: Bearer <刘总 user_access_token>
  过期前用 refresh_token 静默续期（约 2h/次，refresh_token 约 30 天）
```

- **令牌保管**：`refresh_token` 仅存服务器；`access_token` 内存缓存，不落盘；续期失败告警。
- **调用封装**：新增 `feishuAuth.service.ts` 提供 `getValidUserToken()`，业务层无感调用。
- **复用闸门**：`appId`/`appSecret`（api-config）复用为 **OAuth client 凭证**（A）；user_access_token 获取/续期逻辑为**新建**（B）。

### 2.2 设计逻辑（为何选单身份）

| 设计目标 | 单身份模型如何满足 |
|---------|------------------|
| 免成员开通 | 不为 10 名成员逐个申请飞书权限，节省开通/回收管理成本 |
| 记录来源一致 | 所有飞书文档"作者"统一为刘总，无多作者碎片化 |
| 集中读写 | 一处令牌管全部读写，权限边界清晰（只刘总一人可控） |
| 数据统一 | 不存在"某成员令牌失效导致他的记录写不进"的分裂风险 |

**一句话逻辑**：用"牺牲飞书侧细粒度身份"换取"零成员开通成本 + 来源绝对统一"，适合"集中归档、老板主责"的管理模式。

## 3. 为何在多人协作场景下显复杂 / 绕弯

> 本节客观剖析。以下"绕弯"均源于"所有操作共用刘总一人身份"这一核心设定，非实现缺陷。

### 3.1 身份单点 → 作者混淆，溯源需回 OA
- 飞书文档 author 永远是刘总。A 销售写的跟进，推到飞书后**看起来是刘总写的**。
- 想区分"真实操作人"只能依赖文档正文里的**元信息表「操作人」字段**，飞书原生作者/筛选全失效。
- 多人协作时"按作者筛飞书文档"不可能，必须回 OA 的 `feishu_sync_log` 表查。

### 3.2 限流瓶颈 → 全员挤一个令牌额度
- 飞书 `user_access_token` 是**单用户速率上限**（远低于应用身份 tenant 额度）。
- 11 人同时触发自动同步 → 所有请求挤在刘总一个令牌上排队，批量任务互相抢额度，需指数退避。
- tenant_access_token（应用身份）无此瓶颈——这是单身份模型最现实的性能绕弯。

### 3.3 可用性单点 → 刘总令牌即全公司命门
- 刘总 `refresh_token` 失效 / 账号异常 / 离职 → **全公司飞书同步全瘫**。
- 应用身份（appSecret 不变）无此单点。续期机制能缓解但不能消除。

### 3.4 权限不可细分 → 飞书侧 RBAC 失效
- 无法让"某销售只看自己客户的飞书归档"——所有访问都用刘总令牌，要么全有要么全无。
- 细粒度数据隔离只能在 OA 层做，飞书侧是一锅烩。

### 3.5 检索溯源绕弯 → 两步跳跃
- 想在飞书搜"张三跟进的某客户记录"：搜不到（作者是刘总）。
- 必须：OA 内按 OA 操作人查 `feishu_sync_log` → 拿到飞书直链 → 跳飞书看正文。**两系统跳跃**。

### 3.6 合规审计混淆
- 飞书原生审计日志全是刘总一人，无法区分真实操作人；合规追溯需 OA 日志 + 飞书文档元信息**跨系统拼接**。

## 4. 实际使用限制（硬性）

| # | 限制 | 影响 |
|---|------|------|
| L1 | 单用户速率上限 | 高频/批量同步需排队退避，吞吐量受限 |
| L2 | 可用性绑死刘总账号 | 刘总令牌异常 = 全公司飞书能力中断 |
| L3 | 飞书侧无作者区分 | 无法在飞书内按真实操作人筛选/审计 |
| L4 | 权限不可细分 | 飞书侧无法做成员级数据隔离 |
| L5 | 授权耦合 | 重定向 URL、scope 错配会导致全功能不可用 |
| L6 | 离职/转岗风险 | 刘总飞书账号变动需重新授权并迁移历史归属 |

## 5. 可优化方向（演进路线，尊重当前决策）

> 以下均**不违背**"统一身份、免成员开通"核心诉求，作为未来规模/合规升级时的选项。

**OPT-1：写入用应用身份，读取/授权用个人（推荐演进）**
- 建节点 / 写正文改用 `tenant_access_token`（额度高、无单点）；仅"需以刘总身份"的高权限场景用 user_access_token。
- 飞书官方推荐模式，直接消解 L1/L2/L3 中的额度与单点问题，同时保留"统一身份"表象。

**OPT-2：身份映射表（OA-user ↔ 飞书 open_id）**
- 文档 author 用应用身份写（稳定），正文元信息 + 飞书 `@提及` 真实操作人；open_id 写入文档，飞书内可用"提及"区分来源。
- 兼顾限流稳定与溯源清晰。

**OPT-3：可选成员级 OAuth（按需开启，非强制）**
- 默认全员走统一身份；需要飞书侧细粒度权限的成员（如管理员）可单独授权，不强制全员。
- 不破坏"免成员开通"初衷，只给确需者开。

**OPT-4：混合总闸**
- 默认应用身份写，个人令牌作"授权源 / 高权限操作"，失败时回退个人令牌。

## 6. 结论与建议

- **当前决策成立性**：在"集中归档、老板主责、免成员开通、来源绝对统一"诉求下，单用户统一身份是**合理且简洁**的选择，落地成本低。
- **主要代价**：限流瓶颈（L1）、可用性单点（L2）、飞书侧作者/权限不可分（L3/L4）是结构性绕弯，靠 OA 层补偿（sync_log、元信息表）缓解但不根治。
- **演进触发条件**：当①多人高频并发写入导致限流频繁、②合规要求飞书原生区分操作人、③刘总账号变动频繁时，建议启用 OPT-1（应用身份写入）作为首选演进。
- **落地前必做**：刘总提供现有空间 `space_id` + 开放平台登记重定向 URL + 一次性 OAuth 授权；之后按蓝图 Phase 0/1 落地。
